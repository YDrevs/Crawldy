# Калібрувальний бенчмарк Crawldy

Внутрішній інструмент. Не частина продукту, у продуктові шляхи не
імпортується, клієнту не видно.

## Навіщо

Один сайт не відповідає на питання, чи правильний чек. Відповідають два
розподіли: на скількох сайтах він спрацював і які значення бачив там, де
не спрацював. Без другого «поріг 0.8» не можна ні підтвердити, ні
спростувати — видно лише те, що поріг уже пропустив.

Бенчмарк проганяє **справжній рушій аудиту** по списку сайтів і складає
дані в форму, придатну для статистики. Логіки чеків тут немає й бути не
може: інструмент, який відтворює детектор, міряє себе.

## Що вважається базою

Коміт `905970c`, `scoring_version = 3fdd28054fda` і поточний
`detector_version` — заморожена доколібрувальна база. Кожен рядок
результату несе ці ідентифікатори **поруч із сайтом**, а не в шапці
файлу: два набори з різними правилами не можна звести мовчки, і аналіз
кричить, якщо вони змішані.

## Архітектура

| Модуль | Що робить |
|---|---|
| `manifest.py` | корпус: адреси, сегменти, теґи; сталі `site_id` |
| `config.py` | конфігурація прогону, походження, детермінований `run_id` |
| `guard.py` | тверда заборона платних викликів |
| `runner.py` | прогін із продовженням, межами та ізоляцією збоїв |
| `results.py` | JSONL-сховище й знімки одного прогону |
| `measurements.py` | сирі величини детекторів, навіть коли ті мовчать |
| `failures.py` | класи збоїв: чия це проблема — сайту чи наша |
| `analyzer.py` | розподіли, зрізи, викиди, застереження |
| `review.py` | детермінована черга прикладів для людини |
| `cli.py` | `run` / `retry` / `analyze` / `review` |

## Корпус

YAML або JSON. Формат поблажливий: рядок з адресою — вже валідний запис.

```yaml
sites:
  - url: https://example.com
    segment: saas            # saas | ecommerce | local | publisher |
                             # documentation | enterprise | other
    tags: [spa, multilingual]
    enabled: true
    note: чому цей сайт у корпусі
  - https://plain-entry.example
```

`segment` і `tags` — **гіпотеза людини**, а не виміряна властивість. З
домену вони не виводяться (`.io` не означає SaaS), жоден чек їх не
бачить, і потрібні вони лише як розріз в аналізі.

## Запуск

```bash
python scripts/benchmark/cli.py run --corpus scripts/samples/corpus.yaml
python scripts/benchmark/cli.py run --corpus … --limit 5      # шматком
python scripts/benchmark/cli.py retry --corpus …              # лише збої
python scripts/benchmark/cli.py analyze --run <run_id>        # або шлях
python scripts/benchmark/cli.py review  --run <run_id>
```

`--run` приймає ідентифікатор прогону або шлях до його теки. Прогону,
якого немає, інструмент **не вигадує**: раніше сховище створювало
порожню теку й аналіз повідомляв «немає рядків» — тобто описував себе, а
не прогін. Тепер це помилка з переліком наявних прогонів.

`run` без прапорців **продовжує** початий прогін. Ідентифікатор
детермінований за складом корпусу, конфігурацією й комітом: той самий
трійник — той самий каталог і ті самі пропущені сайти. Змінилося
будь-що — це інший прогін.

Журнал тримає **усі** спроби, аналіз рахує **сайти**. Без цього поділу
повторений сайт потрапляв і в успішні, і в збійні: пілот на шести сайтах
показував «8 рядків, 5 успішних, 3 збої», а на тисячі з повторами частка
збоїв була б завищена рівно на кількість повторів. Скільки сайтів
пройшли лише з другої спроби, аналіз каже окремо — це нестабільність
вимірювання, і ховати її не можна.

`retry` торкається лише збоїв, які бувають тимчасовими. 403 і приватний
IP другого разу не зміняться, а внутрішній виняток повторить сам себе —
ховати власний дефект повтором не можна.

## Формат даних

```
benchmark/runs/<run_id>/
    run.json           шапка: конфігурація, походження, що заблокував гард
    results.jsonl      по рядку на сайт
    snapshots/<id>.json  знімок для перегляду без повторного краулу
    analysis.json      вивід `analyze`
    review.json        вивід `review`
```

Рядок результату несе: `site_id`, `url`, `run_id`, сегмент і теґи, час,
`outcome`, клас збою, походження, конфігурацію, статус аудиту, бал,
бали модулів, покриття, деградації, знахідки з кодом/варіантом/
серйозністю/впевненістю/доказом, **сирі вимірювання** і імʼя знімка.

JSONL навмисно: дописування атомарне на рівні рядка, тож перерваний
прогін лишає файл читаним. Обірваний останній рядок пропускається, а не
валить набір.

## Сирі вимірювання

Найцінніша частина. Пишуться завжди, незалежно від того, чи спрацював
чек: довжини ланцюгів перенаправлень, покриття карти сайту, розподіл
подібності сторінок, кількість посилань, видимих лише після рендеру,
класи змішаного вмісту, кодування й версії протоколу, кількість цілей на
підпис посилання. Саме на таких числах ухвалено рішення пунктів #9 і
#11 — і без них вони були б здогадом.

## Класи збоїв

`dns`, `connection`, `tls`, `timeout`, `access_denied`, `unsafe_target`,
`empty_crawl` описують світ. `renderer`, `site_timeout`, `internal` —
нас. Аналіз рахує другі окремо й попереджає: це дефекти прогону, і
робити з них висновки про сайти не можна.

## Жодних платних викликів

`guard.install()` викликається на початку кожного прогону й:

1. вимикає `llm_enabled` і `enrich_enabled`;
2. **підміняє самі модулі** `anthropic` і `openai` у `sys.modules`.

Друге головне: SDK імпортуються ліниво всередині методів провайдерів,
тож підміна модуля перехоплює будь-який шлях — і теперішній, і той, який
хтось додасть завтра, не знаючи про цей файл. Спроба створити клієнт
кидає `PaidCallBlocked`, прогін зупиняється, кредит не витрачається.

Прогін **не починається**, якщо гард не став: `is_installed()`
перевіряється до першого сайту.

Платну інтеграцію, якщо вона колись знадобиться, запускають окремо й за
окремим погодженням.

## Межі ресурсів

- `concurrency` за замовчуванням 3: кожен аудит тягне свій браузер;
- `site_timeout_s` 300 с на сайт, включно з рендером;
- бюджет диска 20 ГБ — прогін спиняється свідомо, а не заповнює диск;
- краул і рендер лишаються продуктовими. Прискорювати бенчмарк
  агресивнішим краулом не можна: тоді міряється не той продукт, що
  працює в проді.

Останнє не побажання, а вже сплачена помилка: калібрування ходило на 8
сторінок замість продуктових 25, і «жодного спрацювання `topic_islands`»
описувало бюджет, а не чек. Тому `RunConfig.deviations()` порівнює
прогін із продуктовим бюджетом, і кожне відхилення кричить **двічі** —
на старті прогону й у застереженнях `analyze`. Аналіз читають окремо від
запуску й через місяці після нього, тож знати команду запуску напамʼять
читач не зобовʼязаний.

Урізаний бюджет законний для перевірки самої інфраструктури й
недопустимий для висновків про правила.

## Як це читатиме калібрування

1. `analyze` дає розподіли й перелік того, що варто подивитися очима.
2. `review` дає детерміновану чергу прикладів: де чек спрацював, де
   мовчав **маючи дані**, і де величина близька до порога.
3. Людина дивиться приклади й вирішує. Інструмент рішень не ухвалює:
   «спрацював на 96% сайтів» буває і правдою (`seo.render_delta` на
   кожному SPA), і вадою (`perf.responsive_images` карав SVG-іконки).
   Розрізнити може лише погляд на приклади.
4. Рішення про ваги й пороги записуються в §K.4 звірки покриття.

## Корпус на 1000 сайтів

`scripts/samples/corpus1000.yaml` **згенерований**, а не набраний руками.
Ланцюг із трьох кроків, кожен зі своїм файлом:

```bash
python scripts/samples/harvest_corpus.py benchmark/candidates.json
python scripts/samples/probe_corpus.py  benchmark/candidates.json benchmark/probes.json
python scripts/samples/build_corpus1000.py
python scripts/benchmark/cli.py validate --corpus scripts/samples/corpus1000.yaml --expect 1000
```

### Звідки беруться сайти

**Wikidata, властивість P856 «офіційний сайт».** Не цитата в статті й не
здогад: хтось звірив, що адреса належить саме цій організації. Разом із
нею беруться `P31` (чим сутність є) і `P17` (країна) — тобто **сегмент і
географія приходять із джерела**, а не з нашої інтуїції.

Перша спроба складала корпус із адрес, які модель памʼятає. Від неї
відмовились, і причина важливіша за зручність: памʼять добре тримає
помітне — університети, музеї, національні медіа — і майже не тримає
звичайного малого бізнесу, заради якого корпус і потрібен. Гірше:
правдоподібний домен, якого не існує, з памʼяті виходить так само
впевнено, як справжній.

Невелика частина записів (документація, вебзастосунки) додана переліком:
у таких сайтів рідко буває стаття у Wikidata. У них `source: curated`, і
вони проходять ту саму живу перевірку.

### Чому обовʼязкова жива перевірка

Wikidata знає, кому належить адреса. Вона не знає, чи адреса сьогодні
відповідає, чи сайт переїхав і чи це взагалі окремий сайт. `probe_corpus`
питає кожного кандидата:

- **існує?** не відповів — не потрапив. Мертвими доменами вибірку не
  наповнюємо: збої заради збоїв нічого не показують;
- **куди веде?** ключем стає хост ПІСЛЯ перенаправлень, тож два домени,
  що ведуть на третій, — це один запис, а не два;
- **на чому зроблений?** теґи ставляться лише за побаченим: `wp-content`
  у відповіді або `<meta generator>`. Мова — з `<html lang>`, тобто заява
  сайту, а не здогадка за доменною зоною.

### Що перевіряє `validate`

Структурні помилки валять перевірку: не та кількість, однакові `site_id`,
однакові нормалізовані адреси, зламані URL.

**Неповнота міток перевірку не валить.** Невідома країна чи порожні теґи
означають рівно те, що написано: джерело не сказало, ми не побачили.
Червона перевірка через невідому мітку заохочувала б її вигадати — і
після цього жоден зріз за мітками нічого не означав би.
