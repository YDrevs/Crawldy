# CLAUDE.md

Контекст проєкту для Claude Code. Читай цей файл перед першою зміною коду.

## Що це

SaaS-агент, який за URL робить аудит сайту в шести вимірах і повертає скор 0..100 з переліком проблем, доказів і рекомендацій:

- **Швидкість / UX** — LCP, INP, CLS, TTFB, render-blocking, зображення, вплив third-party.
- **Базове SEO** — title, meta description, H1-H6, canonical, robots.txt, sitemap, індексованість, внутрішні лінки.
- **AI-ready / LLMO** — llms.txt, JSON-LD, entity signals, FAQ/HowTo/Organization/LocalBusiness schema, граф `@id`, OG і Twitter card.
- **Придатність до цитування** — структура контенту, пряма відповідь, About/Contact/Brand, авторство. Саме придатність, а не факт цитування: зовнішнього тестування промптами ми не робимо, і назва не має цього обіцяти.
- **Захист і аналітика** — security-заголовки, лічильники, захист форм, кешування, 404, редиректи, узгодженість контактів.
- **Доступність** — з Lighthouse тим самим запитом, що й швидкість: окремо те, що ламає користування, і те, що лише ускладнює.

Це реальний продукт, а не демо-скрипт. Пріоритет — коректність, підтримуваність і звітність, підкріплена доказами.

## Поточний стан

Фази 0–3 завершені: звіти (JSON + Word у трьох варіантах під трьох читачів, укр/англ), кілька URL на аудит, публічні посилання, UI, Playwright-рендер, семантичний шар на Anthropic API, готовий llms.txt.

Повний набір backend-тестів проходить без помилок. `ruff`, `mypy --strict app/audit app/core` чисті. 80 чеків у шести модулях. Наскрізний прогін `POST /v1/audits` → Redis → ARQ → Postgres → звіт перевірено на живому стеку.

Інверсію калібрування (занедбана пекарня обганяла stripe.com) виправлено другою стелею на код — див. «Скоринг» нижче.

**Не переписуй існуючий шар аудиту з нуля.** Він покритий тестами й відкалібрований. Розширюй.

Детальні рішення — в `ARCHITECTURE.md`, план фаз — у `ROADMAP.md`.

## Performance-модуль

Без `PSI_API_KEY` запити йдуть у спільну анонімну квоту Google і впираються в 429. Ключ безкоштовний (25 000 запитів/добу, картка не потрібна):

```bash
echo "PSI_API_KEY=ваш-ключ" >> backend/.env
```

Без ключа модуль усе одно живий: працюють статичні евристики з HTML і `perf.server_response` — медіанний TTFB із власних вимірювань краулера. Оцінка тоді `partial`.

## Стек

Python 3.12, FastAPI, ARQ (Redis), PostgreSQL 16, SQLAlchemy 2.0 async, Alembic, httpx, selectolax, structlog. Фронт — Next.js 15 + Tailwind.

Свідомі відхилення від типового вибору, **не змінюй їх без обговорення**:

- **ARQ, не Celery** — asyncio-native, увесь краулер async, Celery тут дав би зайвий шар.
- **selectolax, не BeautifulSoup** — у 5–10× швидший на нашому обсязі парсингу; API вужчий, але покриває наші потреби.
- **Playwright додається у фазі 2**, а не зараз — 80% сигналів є у статичному HTML, і headless-браузер на кожну сторінку коштує дорого. Він потрібен для JS-рендерингу, waterfall і third-party impact.

## Архітектурні інваріанти

Порушення будь-якого з них — це баг, навіть якщо тести зелені.

1. **`app/audit/` не імпортує ні FastAPI, ні SQLAlchemy.** Це чисте ядро: на вході URL, на виході `AuditOutcome`. Саме тому чеки тестуються без БД і без мережі. Enum'и живуть в `app/audit/enums.py`, а не в моделях, саме через це.
2. **API-процес не робить зовнішніх мережевих викликів для аудиту.** Тільки постановка задачі в чергу й читання результатів. p99 API має лишатися < 100 мс.
3. **Парсинг відокремлений від оркестрації.** `extractor.py` перетворює HTML на `PageSignals` і більше нічого не знає. Чеки працюють лише з `SiteContext` — вони не ходять у мережу.
4. **Кожна проблема має докази.** `Issue.evidence` заповнюється завжди: що знайдено, що очікувалося. Звіт без доказів не переконує клієнта.
5. **Дані Lighthouse/crawl не вигадуються.** Якщо провайдер не відповів — модуль виключається зі скора, аудит стає `partial`, у звіт іде `missing_data`. Ніяких заглушок із правдоподібними числами.
6. **Падіння одного чека не валить аудит.** Оркестратор ловить виняток кожного чека окремо й пише його в `degraded`.

## Головна точка розширення: новий чек

```python
# app/audit/checks/seo.py (або ai_ready.py / llm_visibility.py / performance.py)

@register
class MyCheck(Check):
    code = "seo.my_check"          # унікальний, крапкова нотація, реєстр падає на дублі
    module = Module.SEO
    severity = Severity.MEDIUM     # дефолт, можна перевизначити в self.issue(...)
    weight = 2
    effort = Effort.LOW            # скільки коштує фікс; ділить impact у звіті
    messages = ("seo.my_check",)   # ключі каталогу; дефолт — сам code
    reads_content = True           # чи потрібен прочитаний вміст, щоб висновок був вагомим
    variants = ("a", "b")          # семантично різні проблеми, які чек розрізняє

    def run(self, ctx: SiteContext) -> Iterable[Issue]:
        for page in ctx.ok_pages:
            if problem_detected(page):
                yield self.issue(
                    params={"count": 3},
                    evidence={"found": ..., "expected": ...},
                    page_url=page.url,
                )
```

**Чек не пише текст.** Рядки — в `app/audit/i18n/uk.py` і `en.py`, чек віддає ключ і параметри:

```python
"seo.my_check": {
    "title": "Знайдено {count} проблем",
    "description": "Чому це проблема.",         # для спеціаліста
    "recommendation": "Що конкретно зробити.",  # для спеціаліста
    "consequence": "Що це коштує бізнесу.",     # для керівника, без жаргону
},
```

`variants` оголошує проблеми, які чек уміє розрізняти. Порожньо — чек знає
одну проблему, і `issue_key` дорівнює коду. Непорожньо — кожна знахідка
мусить назвати свою: `self.issue(key="lcp", ...)`, і `issue_key` стане
`perf.core_web_vitals:lcp`. На `issue_key` тримається стеля штрафу й
групування рекомендацій, тож поділ — це зміна скорингу, а не оформлення.
Ключі каталогу для цього не годяться: їх перейменовують разом із текстом.

`reads_content` вирішує, чи потрапить знахідка у звіт, коли краул не приніс
жодної сторінки. Дефолт `True` — більшість чеків судить прочитане, і його
твердження про відсутність тоді описує нашу відмову, а не сайт. `False`
ставлять чекам, чий доказ лежить у самій відповіді сервера: код, заголовки,
сертифікат. Такий доказ лишається доказом і без сторінки.

`consequence` обовʼязковий і не містить жаргону — з нього складається нетехнічна частина Word-звіту. Тест `test_consequence_avoids_the_jargon_of_the_technical_wording` не пропустить `canonical`, `JSON-LD`, `H1`, `LCP` тощо.

Реєстрація автоматична через `@register`, скоринг підхопить чек без змін. **Порожній результат = чек пройдено.** Ваги не хардкодяться в логіці — вони в атрибутах класу й у `scoring.py`, щоб калібрувати без правок чеків.

До кожного нового чека — тест у `tests/test_checks_*.py`: один на спрацювання, один на «чиста сторінка не дає issue». Плюс `test_i18n` вимагає, щоб **синтетичний контекст чіпляв кожен новий ключ** — інакше його шаблон ніколи не перевіриться на відповідність `params`.

> за недоведене бали означало б продавати здогад), `get_method` —
> MEDIUM × вага 3. Жодна константа формули не змінилась. Виміряно на 50
> знімках: 16 сайтів із формою заявки, 5 із них на GET, знахідка
> спрацювала на всіх пʼятьох, зсув бала −2…−3, модуля tech −11…−20,
> сайтів без знахідки не зрушило жодного. `SCORING_RULES` піднято до 4,
> `DETECTOR_RULES` — до 2: бали по різні боки цієї межі непорівнянні, і
> обидва відбитки це показують. Збережені аудити не перераховані.


```
penalty      = Σ(weight × severity_multiplier)          , дві стелі на один issue_key
module_score = 100 × half_scale / (half_scale + penalty)
overall      = Σ(module_score × MODULE_WEIGHT[module])
```

**Ваги тут навмисно не переписані числами.** Єдине джерело —
`MODULE_WEIGHT` у `backend/app/audit/scoring.py`; його знімок для
публічної сторінки лежить у
`frontend/app/content/methodology/scoring-facts.json` і звіряється з
реалізацією тестом `backend/tests/test_methodology_page_facts.py`.

Дублювання чисел у документації вже дало розходження: тут стояли
`0.22 / 0.22 / 0.18 / 0.18 / 0.10 / 0.10` — ваги ДО калібрування night3
(сценарій F, затверджено 2026-08-31), тоді як продукт рахував SEO 0.26,
performance 0.18, ai_ready 0.16, tech 0.16, llm_visibility 0.14,
accessibility 0.10. Чинні числа завжди дивись у коді або в знімку; третє
місце зберігання розійшлося б із першими двома так само.

Шкала гіперболічна, а не лінійна: вона монотонна й **ніколи не досягає нуля**. `half_scale` — це штраф, за якого модуль опускається рівно до 50.

Лінійний варіант із `clamp 0..100` дав реальний дефект: сайт, що вдвічі перевищує норму, отримував 0 по всіх напрямах і лишався на нулі навіть після половини виправлень — повторний аудит не показував прогресу, заради якого його й замовляють. Значення `half_scale` підібрані так, щоб типовий сайт лишився на тій самій оцінці (python.org — 52).

Множники: critical 5, high 3, medium 2, low 1, info 0.

**Стеля береться від найважчої знахідки групи, а не від останньої.** Поки ліміт рахувався від поточного issue, менш серйозна знахідка в тій самій групі **знижувала** штраф: сайт із блокуючою вадою доступності мав 57, а той самий сайт із блокуючою плюс звичайною — 67, і результат залежав від порядку перебору.

**Три ідентифікатори, а не два.** `code` — категорія детектора (`perf.core_web_vitals`). `issue_key` — конкретна проблема (`perf.core_web_vitals:lcp`), і саме на ній тримаються стеля штрафу й групування рекомендацій. `msg` — рядок каталогу, тобто presentation layer: він міняється разом із формулюванням і ідентифікатором бути не може.

**Дві стелі на один `issue_key`.** Перша відносна — 2× від самої знахідки: одна проблема на 20 сторінках не має занулювати модуль. Друга — `MAX_PENALTY_SHARE_OF_HALF` від `half_scale` модуля: жодна окрема проблема не вирішує модуль одноосібно. Без другої важкий чек обходив першу — `ai.jsonld.missing` давав 48 при `half_scale` 30 і сам опускав `ai_ready` до 38, через що сайт на WordPress обганяв stripe.com. Одиночна знахідка рахується завжди повністю: стеля приборкує повторення, а не силу проблеми.

Смуги інтерпретації для звітів і UI:

| Діапазон | Оцінка |
|---|---|
| 0–39 | critical |
| 40–59 | poor |
| 60–79 | medium |
| 80–100 | good |

Пропущений модуль (немає даних) виключається з `overall`, а не зараховується як нуль.

**Три стани покриття модуля**, не два:

| Стан | Коли | У скорі | У звіті |
|---|---|---|---|
| повний | усі сигнали зібрано | так | звичайна оцінка |
| `partial` | частина сигналів відсутня, але щось виміряли самі | так | `ScoreEntry.partial`, застереження в `missing_data` |
| `skipped` | вимкнено користувачем або даних немає взагалі | ні | `speed_score: null` |

Приклад: без ключа PSI немає Core Web Vitals, але час відповіді сервера ми міряємо самі на кожній сторінці — модуль стає `partial`, а не зникає.

Пайплайн: `resolve → site_context → crawl → extract → checks → score → persist`.
Звіт: `AuditOutcome | рядки БД → ReportSource → ReportDocument → JSON | docx`.

**Документів чотири, а не два.** Аудит і присутність — окремі продукти з
окремими методологіями, і кожен виходить у двох видах: **загальний**
(власнику, без термінів) і **технічний** (спеціалісту, з доказами).
Назви видів затверджені власником 2026-09-06 і стоять на обкладинці, у
назві файлу й на кнопках; попередні «для власника» / «для спеціаліста»
не вживаються ніде. Дані двох видів одного предмета збираються ОДНИМ
шляхом (`application/presence._payload`, `report_service.source_*`) —
інакше два документи про той самий прогін розійшлися б числами.
Збагачення: `детерміністична правда → вхід задачі → маршрут → провайдер →
валідація → журнал`. Воно **не має шляху назад**: змінити знахідку,
серйозність чи бал звідти неможливо, і це властивість контракту, а не
дисципліни. Вимкнене (`ENRICH_ENABLED=false`) і потребує ще й явного
внутрішнього тригера — жоден маршрут API його не передає.

## Пастки, на які вже наступали

- **Порядок в `extractor.extract()` має значення.** `_extract_text()` викликає `decompose()` на script/style, тобто руйнує дерево. Він іде **останнім**, після витягування JSON-LD і perf-підказок. Якщо додаєш новий екстрактор, що читає `<script>` — став його до `_extract_text`.
- **`AuditPage.id` генерується вручну** в `persist_outcome()`. Python-side `default=uuid4` спрацьовує лише на flush, а нам треба зв'язати issue зі сторінкою до нього.
- **Точка входу вантажиться один раз.** Оркестратор тягне її, щоб визначити origin і HSTS, і передає у `crawl(prefetched=...)`. Не роби другий запит.
- **SSRF-перевірка на кожному редіректі**, не лише на вхідному URL. `assert_public_host` викликається і для `response.history`.
- **`alt=""` — валідно** для декоративних зображень. Рахуємо лише повну відсутність атрибута.
- **`robots.txt`, що віддає HTML** — поширений випадок 404-сторінки зі статусом 200. Перевіряй `content-type`, а не лише код.
- **Скор не залипає, але `floored` лишається.** Гіперболічна шкала не досягає нуля, тож пріоритезація працює завжди. Прапорець `floored` у рекомендаціях уцілів для випадку, коли округлена дельта все одно виходить 0 — краще сказати «бал майже не зросте», ніж малювати фальшивий «+1».
- **`impact_points` не можна сумувати.** Кожен міряний окремо проти того самого базового скора; стеля на `code` і clamp роблять ефект нелінійним. У JSON про це каже `summary.impact_is_independent`.
- **Порядок рекомендацій — не лише вигода на вартість.** Спершу смуга серйозності (низька впевненість опускає на смугу нижче), а всередині смуги — вигода, помножена на важливість сторінки з графа посилань. Важливість береться максимумом по групі: проблема, що є і на головній, лишається проблемою головної.
- **Рекомендації й стеля штрафу групуються по `issue_key`.** Один `code` віддає різні проблеми («немає title» проти «title закороткий») — для клієнта це різні дії, і бал мусить рахувати їх так само. `msg` — presentation layer: він міняється разом із формулюванням і ідентифікатором бути не може. Раніше тут стояв саме `msg`, і поділ виходив правильний із неправильної причини.
- **Модуль, вимкнений користувачем, — не збій.** `Degradation.is_failure` розводить `MODULE_EXCLUDED` і справжні збої, інакше будь-який аудит із фільтром модулів ставав би `partial`.
- **structlog пише повз `logging.basicConfig`** — через власну `PrintLoggerFactory`. Щоб логи не потрапили в stdout поруч із JSON, `configure_logging()` треба передати stream.
- **Консоль Windows у cp1251** ламає українські рядки й валить процес на `←`. У CLI та `conftest.py` stdout примусово переведений на UTF-8.
- **Порядок INSERT'ів SQLAlchemy будує за `relationship`, а не за FK на рівні таблиць.** Без `relationship` між `AuditIssue` і `AuditPage` issues летіли в базу раніше за сторінки, на які посилаються, і Postgres відбивав їх `ForeignKeyViolationError`. Тримаємо і relationship, і явний `flush()` між ними.
- **Воркер не має hot-reload.** API з `--reload` підхоплює правки сам, `arq` — ні. Після зміни пайплайну чи чеків обовʼязково `docker compose restart worker`, інакше воркер мовчки виконує стару версію.
- **Bind-mount у Docker Desktop на Windows не пробиває inotify.** Next у контейнері не бачить змін у `frontend/` — потрібен `docker compose restart frontend`.
- **`.env` з `API_KEYS=...` валив старт**, поки `api_keys` не отримав `NoDecode`: pydantic-settings пробує `json.loads` для `list[str]` ще до валідаторів.
- **Секрети не логуємо.** PSI приймає ключ лише в query, а httpx на INFO пише повний URL. У `app/core/logging.py` стоїть редагування — при додаванні нового провайдера з токеном перевір, що він під нього підпадає.
- **Порожній результат чека ≠ «все добре».** Сайт, що віддав агенту 403, не дає жодної знахідки — і без окремої перевірки виходив на перше місце у своїй групі. `_module_coverage` виключає контентні модулі, коли `ctx.ok_pages` порожній, і робить це **до** фільтра модулів: сліпота не залежить від того, які модулі замовили.
- **`ctx.ok_pages` не годиться для чеків про доступність.** `tech.crawler_blocked` читає `ctx.pages`, бо йому потрібні саме сторінки, які контенту не віддали. Це єдиний чек, який працює, коли не працює жоден інший.
- **Маркери аналітики шукаються по `src`, `href` та inline-коду, але не по видимому тексту.** Інакше стаття блогу з рядком `google-analytics.com` зараховується за встановлений лічильник. Тест `test_article_about_analytics_is_not_counted_as_an_installed_counter` це фіксує.
- **Пошук підрядка в HTML бреше.** Слово `cheaper` містить `heap`, а Next.js-чанк `layout-segment-context` містить `segment`. Перш ніж робити висновок з наявності маркера, дивись його контекст.
- **Підрядок в URL бреше так само, як у HTML.** У `/legal/ssa-services-terms` є «services», і краул на stripe.com приносив дванадцять сторінок договорів замість сторінки з цінами. Слова шляху розбираються окремо — `page_kinds.path_words`.
- **Фасети магазину мають порожній шлях.** `?orderby=`, `?per_page=`, `?shop_view=` — це та сама головна, і без окремої перевірки вони отримували пріоритет головної сторінки й зʼїдали весь бюджет краулу.
- **Google виконує JS, асистенти — ні.** SEO-чеки дивляться на `ctx.as_seen(page)` (після рендеру), чеки ai_ready і llm_visibility — на статичну версію. Це не вибір зручності: один і той самий факт коштує різного різним читачам.
- **`effort` приймають не всі моделі.** Haiku 4.5 відповідає на нього 400. Оскільки збій API аудит не валить, шар мовчки вимикався, і це виглядало як «модель нічого не знайшла».
- **Твердження «цього немає ніде» вимагає, щоб ми там дивилися.** `llm.unstated_facts` мовчить, якщо сторінка з фактом на сайті є, але в бюджет читання не потрапила. Знахідка без доказу гірша за пропущену.
- **Вибір моделі змінює бал, а не лише ціну.** На 1csmart.com.ua різниця між Opus 5 і Haiku 4.5 — 13 балів. Тому модель — параметр аудиту й лежить в його опціях, а не в `.env`.
- **Карту сайту не можна брати початком.** `urls[:5000]` — це «те, що сайт випадково поклав першим». На furniturerow.com початок карти зайнятий тисячами товарних адрес із GUID, і зі 112 сторінок магазинів у зріз потрапляла одна. Береться рівномірна вибірка по всій довжині, а службовим сторінкам віддано частину місць окремо: рівний крок не ловить клас, який складає півтора відсотка.
- **Аудит бачить не сайт, а свою вибірку.** Найдорожча помилка проєкту досі — не хибний чек, а порада додати розмітку, яка в клієнта вже була: сторінку з нею просто не прочитали. Перш ніж повірити знахідці про відсутність чогось, подивись `evidence` — які саме сторінки ми відкривали.
- **Зведення сигналів довіри не вийшло, і це висновок, а не пропуск.** Чек «сайт не каже, хто за ним стоїть» на пʼяти ознаках (назва в розмітці, «про нас», контакт, адреса, соцпрофілі) називав анонімними python.org і backlinko.com. Причина в тому, що ці ознаки міряють повноту розмітки, а не розкриття особи, — і повноту вже міряє ai_ready. Окремі сигнали лишаються окремими чеками.
- **Поле схеми й звʼязок моделі не можуть зватися однаково.** `IssueOut.verdict` тримає enum, а `AuditIssue.verdict` був звʼязком; pydantic із `from_attributes` бере атрибут за іменем і падав на ORM-обʼєкті. Ендпойнт аудиту віддавав 500 — але лише після появи першого записаного вердикту, тобто на живому стеку й не одразу. Звʼязок тепер `human_verdict`.
- **Контраст провалюють майже всі, тож він не «блокуючий».** `color-contrast` спрацьовував на 17 сайтах із 31, а на шести був єдиною причиною знахідки про зламане користування. Проблема не в тому, що контраст неважливий, а в тому, що Lighthouse віддає сам факт без частки ураженого тексту: нечитабельну сторінку від сірого підпису нашими даними не відрізнити. Тому він у звичайних, а в блокуючих лишилось те, що доводиться однозначно.
- **Не обіцяй того, чого не міряв.** «Видимість для LLM = 93» читається як «ChatGPT згадує вас у 93% відповідей», а ми міряємо придатність сайту до цитування. Напрям перейменовано в звіті (не в базі), а `consequence`-рядки з твердженнями про поведінку асистента переписані на ймовірність. Категоричним лишається лише факт: заборону GPTBot у robots.txt ми прочитали на власні очі. Тест `test_consequence_does_not_promise_what_we_never_measured` тримає межу.
- **Проблема, яка є в усіх, — не програш.** `benchmark` ділить знахідки на три купи: спільні для всіх (норма галузі, виграшу не дадуть), лише ваші (те, за що платять) і лише не ваші (перевага, яку легко втратити). Таблиця балів окремо від цього не каже, що робити. Модулі рівняються на медіану конкурентів, а не на середнє: один заблокований краул інакше перетягує картину.
- **«Відхилено» без причини — марні дані.** `Verdict` розділяє `wrong` («такого немає») і `wont_fix` («правда, але не робитимемо»): проти чека свідчить лише перше. Одна кнопка «відхилити» зробила б обидва однаково нечитабельними, а це єдине джерело зовнішньої правди, яке в проєкту може зʼявитися.
- **Дельта балів без версій нічого не означає.** `history.compare` рахує різницю завжди, але поруч каже, чи змінювалися `detector` і `scoring`: коли так, різниця пояснюється і сайтом, і нами, а розділити внески неможливо. `config` і `model` на це не впливають — вони кажуть, *що* міряли, а не *як* рахували.
- **`to_json()` і знімок — різні речі.** Перший компактний, для звіту: посилання згорнуті в лічильники, розмітка — в перелік типів, тексту немає. Зібрати з нього `SiteContext` назад неможливо. Для перерахунку є `snapshot.py`, і додаючи поле в `PageSignals`, треба памʼятати, що знімок бере всі поля дата-класу автоматично, а `to_json` — ні.
- **Меню є на кожній сторінці, тому не каже про жодну.** `cro.no_action` із підрахунком посилань будь-де не спрацював на жодній із 41 комерційної сторінки восьми сайтів — і не міг: «Контакти» в шапці має кожен. Звідси `LinkRef.in_chrome` (`<nav>` і `<footer>`) і `PageSignals.body_contacts`. `<header>` навмисно лишився тілом: там часто стоїть головна кнопка.
- **`cro.no_action` бачить одну комерційну сторінку на сайт.** Він судить лише про відрендерені сторінки, а бюджет рендеру — три, з яких комерційна гарантовано одна. Мовчання чека означає «на тій сторінці, яку ми відкрили, дія є», а не «дія є всюди». Сам чек перевірений мутацією справжнього знімка: сторінка ka-dent із двома формами мовчить, вона ж без них — спрацьовує.
- **Заклик до дії — не завжди `<a>`.** На moz.com і hubspot.com кнопки домальовує скрипт, тому чек про відсутню дію судить лише про сторінки, які ми справді відкрили в браузері, і бюджет рендеру тепер обовʼязково включає одну комерційну сторінку. Інакше знахідка описувала б наш краул.
- **Спільна ціль посилань — це меню, а не хаб.** Ідея вважати тему звʼязаною, якщо її сторінки ведуть на спільну сторінку-перелік, розбилась об дані: на backlinko.com спільних цілей виявилось сімдесят шість, і всі вони були шапкою сайту. `seo.topic_islands` тому стверджує лише те, що бачив — сторінки однієї теми не згадують одна одну, — і має низьку серйозність із середньою впевненістю.
- **«Ніхто не посилається» — теж твердження про вибірку.** Граф посилань будується з прочитаних сторінок, тож на furniturerow.com із 8147 адрес у карті й 25 у бюджеті кожна друга виглядала б сиротою. `seo.orphan_pages` мовчить, поки ми не прочитали `SITEMAP_COVERAGE_FOR_ORPHANS` карти. `seo.links_to_noindex` гейта не потребує: там ми бачили і посилання, і заборону на власні очі.
- **Таймаут на кожній операції не дорівнює таймауту на всій.** У рендері були обмежені `goto` і очікування мережі, а запуск браузера, `page.content()` і закриття контексту — ні. Аудит не падав, а зависав, і ззовні це не відрізнити від «повільно». Тепер `render()` обгорнутий у `asyncio.wait_for`, а зависла сторінка викидає браузер: наступна на ньому теж має шанс зависнути.
- **Заглушка в User-Agent — ознака скрапера.** `+https://example.com/bot` віддавав 403 на detailtyler.com, хоча його robots.txt дозволяє всім; той самий рядок без адреси проходив. Аудит при цьому поводився правильно — не вигадав бал і назвав причину, — але сайт клієнта лишався непрочитаним через наш власний рядок. Порожньо чесніше за фальшиве посилання. Сайти, які справді захищаються (openai.com, aequo.ua), віддають 403 і без заглушки: це їхнє рішення, і його поважаємо.
- **Класифікація типу сторінки — не те саме, що пріоритет краулу.** `kind_of` каже, що тягнути раніше; `type_of` — що це за сторінка. Правила спираються на друге: `noindex` на `/wp-login.php` доречний, на комерційній сторінці — критичний.
- **Число, переписане в документацію, розходиться з кодом — питання лише коли.** `CLAUDE.md` півтора місяця показував ваги `0.22/0.22/0.18/0.18/0.10/0.10`, скасовані калібруванням night3 ще 31 серпня. Ніхто не помітив, бо тести звіряли код із кодом, а документацію не читав жоден із них. Тепер ваг у прозі немає взагалі: єдине джерело — `MODULE_WEIGHT`, публічна сторінка бере його знімок, а знімок звіряє тест. Правило ширше за цей випадок: якщо число живе у двох місцях, друге має бути похідним і перевіреним, а не переписаним.
- **Захист форм: маркер у розмітці — не доказ захисту, а його відсутність — не доказ дірки.** Побачений `cf-turnstile` доводить лише те, що віджет підключено на клієнті; перевірку токена на сервері пасивним оглядом не видно взагалі (і Google, і Cloudflare прямо вимагають її окремо). Тому детектор каже «видимих ознак не виявлено», а не «форма незахищена», і не дає жодного бала за наявність маркера. Три речі він не робить ніколи: не надсилає форму, не обходить челендж, не перевіряє rate limit — це чужий сервер, і активна перевірка там була б зловживанням, а не аудитом.
- **Маркер, шуканий у HTML цілком, ловить власний текст сторінки.** Перша версія детектора форм брала `node.html` і зараховувала абзац «ми використовуємо reCAPTCHA» за встановлений захист, а слово `trap` у тексті — за honeypot. Ознаки шукаються лише в АТРИБУТАХ (клас, id, name, src, data-sitekey); текст не свідчить ні про що. Той самий клас, що й «Пошук підрядка в HTML бреше».
- **Захист, який домальовує скрипт, зі статики не видно — і це не «його немає».** Turnstile і reCAPTCHA частіше додаються JS, ніж приходять із сервера, тож детектор дивиться і на відрендерену версію. Окремо: бібліотека провайдера, підключена сторінкою (`script[src]`), не доводить, що конкретна форма нею користується, — але й не дає сказати протилежне, бо саме так виглядає невидима reCAPTCHA v3. Такий стан називається `undetermined`, і мовчання в ньому дешевше за хибне звинувачення.
- **Форма, яку домальовує клік, для краулера не існує.** Наша ж контактна сторінка спершу монтувала форму лише після натискання кнопки — і власний аудит Crawldy не бачив на ній ані форми, ані оголошеного Turnstile. Виправлено не тестом, а розміткою: форма присутня завжди, `hidden` ховає її від ока й від фокуса, кнопка знімає прапорець. Продукт, який продає видимість для машин, не має права на цю помилку у себе.
- **Впевненість не однакова.** Статус відповіді й кількість H1 — факти; висновок моделі — судження. `Confidence` знижує знахідку на смугу нижче в пріоритезації, а низька впевненість не пускає її в «Що робити першим».
- **Порядок рекомендацій — спершу смуга серйозності, потім вигода на вартість.** Чиста вигода-на-вартість структурно виносить дешеву косметику над критичним: Twitter-картка стояла першою при Lighthouse 25.
- **Демо-вміст шукається збігом сигналів, а не одним.** Пошта на домені теми буває справжньою, іноземне імʼя в команді — теж. Знахідка від двох різних сигналів, впевненість росте з третім.
- **Стеля повторень частково міряла нас, а не сайт.** 4× від однієї знахідки досяжні лише там, де прочитано багато сторінок: сайт на чотири сторінки фізично не міг набрати повторень, сайт на двадцять чотири набирав завжди. Тепер 2×, і на розширеній вибірці інверсій 23 → 17. Другу стелю пробували знизити до 0.3 (давало 12) і не взяли: при ній стеля стає нижчою за одну знахідку важкого чека, і повторення перестає коштувати взагалі — правило скасовує саме себе.
- **Причин «нема бала» три, а пояснення було одне.** Звіт для власника казав «сайт не пустив нашу програму» і сайту з простроченим хостингом, і сайту, половина якого не відповіла. Вибір тексту тепер за `scope` деградації (`crawl` / `crawl.empty` / `crawl.failures`), а не за смугою оцінки: зіставляти рядок `reason` мовою — шукати халепи.
- **Абсурдне число в даних — це знахідка, а не баг парсера.** `myfriendlythai.ca` дав 111 тисяч слів на сторінці, і я пішов шукати помилку в екстракторі. Помилки не було: сторінка ресторану впиралася в межу завантаження у пʼять мегабайтів, а в тексті лежали тисячі спам-коментарів із чужими посиланнями. Сайт зламано, аудит це прочитав і не сказав ані слова — ваги сторінки не перевіряв ніхто. `perf.page_weight` стверджує лише те, що видно (розмір і обсяг тексту), і називає звичні причини, лишаючи висновок людині.
- **Мало прочитали — не давай упевненого числа.** Два випадки з розширеної вибірки: `oldetownhall.com` віддав єдину сторінку на чотирнадцять слів (повідомлення хостера про призупинення акаунта) і отримав 68 балів; `gocplumbing.com` не відповів на сім адрес з одинадцяти й отримав 64. Тепер контентні модулі виключаються, коли на всьому сайті менше `MIN_WORDS_FOR_A_SITE` слів або коли не відповіла більшість адрес. Частка невдач рахується лише від `MIN_URLS_TO_JUDGE_A_CRAWL` спроб: на краулі з двох адрес одна битва — це вже 50%.
- **«Терміново» в кожному звіті нічого не означає.** У документі для власника `high` мав той самий підпис, що й `critical`, а HIGH-знахідки має майже кожен сайт: `seo.h1` спрацьовує на 21 із 29, `tech.analytics` на 19. На ka-dent пʼять рядків «ТЕРМІНОВО» стояли при нулі критичних знахідок. Тепер у кожної серйозності свій підпис, і тест вимагає, щоб вони не збігалися. Знайдено читанням згенерованого документа — тести на жаргон і плейсхолдери цього не бачили.
- **Критичною може бути лише метрика, яку переживає користувач.** Core Web Vitals три — LCP, INP, CLS; TTFB і TBT діагностичні. Поки будь-яка «poor»-метрика ставала критичною, усі дванадцять критичних TBT на вибірці були лабораторними — симуляція під штучним тротлінгом, — тоді як INP тих самих сайтів, виміряний на живих користувачах, не був критичним жодного разу. Ми ставили наближенню вищу оцінку, ніж вимірюванню, яке воно наближає. Тепер діагностика максимум HIGH, лабораторне джерело знижує впевненість, а за наявності польового INP лабораторний TBT не повідомляється взагалі.
- **Документація — не стаття.** У довідки немає ні автора, ні дати, ні розмітки Article, і це задум, а не недбалість. Розділи `docs`/`guide`/`glossary` спершу жили серед статей — щоб глосарій не ставав послугою через слово «price» усередині терміна, — і це полагодило одне, зламавши інше: від кожної сторінки документації почали вимагати автора й Article. Тепер у неї свій `PageType.DOCS`, і він визначається ще й за піддоменом: `docs.stripe.com/payments/checkout` інакше ставав кошиком через слово «checkout».
- **`srcset` не потрібен вектору.** `perf.responsive_images` рахував усі зображення й спрацьовував на 23 сайтах із 29. На головній ahrefs.com зі 133 зображень 120 — SVG: ми карали сайт за те, що він використовує векторні іконки. Рахуються лише растрові.
- **Підрядок у шляху бреше й тут.** `ai.schema.content_type` зіставляв префікси, тож `/product` ловив `docs.stripe.com/products-prices/…`, а `/news` — `fastapi.tiangolo.com/newsletter/`. Тип сторінки бере `type_of`, і сторінка невпізнаного типу лишається без вимоги: просити Article там, де ми не впевнені, — просити неправдиву розмітку.
- **`noindex` — це вказівка власника, а не поломка.** Ми бачимо саму заборону й не бачимо наміру. Поки чек ставив `critical`, критичними ставали PPC-лендинги Shopify, архів вебінару, закрите демо Cloudflare і варіант контактів Stripe для внутрішнього трафіку — сім сайтів верхнього рівня проти нуля в нижнього, бо в нижнього таких сторінок просто немає. Тепер це MEDIUM із середньою впевненістю й формулюванням «перевірте, чи так задумано»; випадок без сумнівів ловить `seo.links_to_noindex`, де сайт сам веде на закриту сторінку. На тих самих знімках: інверсій 4 → 3.
- **Чек, що спрацьовує на всіх, не розрізняє нікого.** `ai.opengraph` вимагав `og:locale`, якої немає в 59% сайтів вибірки — і майже в усіх верхнього рівня, — тоді як `og:title` і `og:image` бракує лише 7%. Вимогу знято: локаль необовʼязкова, споживачі OG підставляють дефолт. На розділення це не вплинуло (перевірено перерахунком), але звіт перестав називати дефектом те, що ним не є.
- **Калібрування має міряти той краул, який виконує продукт.** `calibrate.py` ходив на 8 сторінок углиб 1, тоді як продукт — на 25 углиб 2. Наслідок не косметичний: `seo.topic_islands` потребує трьох сторінок одного розділу й за такого бюджету не міг спрацювати взагалі, тож «0 з 31» описував бюджет, а не чек. З продуктовим бюджетом він спрацьовує на кожному пʼятому сайті, і спрацювання справжні.
- **Два калібрувальні прогони порівнювати не можна.** Це два різні краули, і розкид між ними більший за більшість змін, які ми оцінюємо: на 29 сайтах медіанний зсув бала — 2, у тринадцяти ≥3, максимум 7, при однаковій кількості прочитаних сторінок. Джерело — Lighthouse із вагою 0.22. Зміну правил оцінюють перерахунком тих самих знімків (`calibrate.py --snapshots`, потім `rescore_dir.py` до і після), інакше читаєш шум і приписуєш його своїй правці. На цьому вже спіймано хибний висновок: пʼять інверсій, які я приписав зміні контрасту, виявились властивістю прогону — A/B на однакових даних дав ту саму пʼятірку в обох варіантах.
- **Рівень сайту у вибірці кодує репутацію, а не машинну читабельність.** `americanhps.wixsite.com` із нижнього рівня має 62 проти 49 у linear.app із верхнього — і це не збій: у них однакове число різних проблем (22 коди), але в linear.app 103 входження проти 36 і гірші швидкість та SEO. Занедбаний бізнес на конструкторі справді читабельніший для машин за складний SPA. Виправляти такі «інверсії» параметрами означає вчити шкалу оцінювати бренд.
- **Бал не відтворюється на сайтах із захистом від ботів.** openai.com в одному прогоні віддав 8 сторінок і 75 балів, у наступному — 403 і 36. Це властивість вимірювання, а не регресія; обходити захист не можна.
- **Вимкнене користувачем — не збій, і це доводиться писати двічі.** У
  `is_failure` давно стоїть виняток для `MODULE_EXCLUDED`, але вимкнений
  семантичний шар писався як `PROVIDER_UNAVAILABLE`, а `llm_enabled` за
  замовчуванням `False` — тож статус `completed` був недосяжний узагалі:
  28 із 35 аудитів валідаційної вибірки виходили `partial` без жодної
  справжньої причини. Тепер є `LAYER_DISABLED`, а `SiteBrief.disabled` і
  `RenderResult.disabled` несуть причину прапорцем. Розбирати рядок
  `error` не можна: причин мовчання чотири, і лише одна з них — вибір.
- **Притримати бал і притримати твердження — різні речі.** Коли краул
  сліпий, контентні модулі виключаються зі скора, але їхні знахідки досі
  йшли в звіт: `unilever.com` віддав 403 на все, бал чесно був `None`, і
  поруч стояло 13 тверджень про сайт, якого ми не бачили. Правдиве було
  одне — `tech.crawler_blocked`. Фільтр у білдері звіту вузький навмисно:
  спрацьовує лише на `CRAWL_BLIND` і лише на чеки з `reads_content`. При
  `CRAWL_FAILURES` ми прочитали меншість адрес, при `CRAWL_EMPTY` —
  отримали HTML без тексту; бачене в обох випадках лишається баченим.
- **`ctx.home` — не `pages[0]`.** Вхідна адреса може відповісти помилкою:
  `bosch.com/this-page-does-not-exist/` віддав 404, краул пішов за
  посиланнями зі сторінки помилки й прочитав справжній сайт, а головною
  лишалась неіснуюча адреса — її title, H1 і розмітку чеки судили як
  головну сторінку компанії. Гірше, що PSI міряє саме вхідну адресу, тож
  модуль швидкості вагою 0.22 описував сторінку 404 при 76 балах у звіті.
  Тепер `home` бере першу, яка справді відповіла, а вхід із 4xx/5xx дає
  деградацію `ENTRY_ERROR`. Фолбек на `pages[0]` лишився для сайту, де не
  відповіла жодна: там 403-відповідь — усе, що ми маємо.
- **Один scope не може означати два стани.** Рядок `"crawl"` позначав і
  «жодної сторінки», і «рівно одна сторінка» — протилежні речі. Поки на
  scope ніхто не спирався, це було нешкідливо; щойно на нього сперся
  фільтр звіту, збіг став би тихою помилкою. Друге тепер `CRAWL_SHALLOW`.
  Та сама помилка, що й дві різні проблеми під одним `code`.
- **Пошук сторінки за адресою карає малі сайти.** `llm.contact_page`
  шукав URL виду `/contact` і на цьому спинявся, тож односторінкова
  пекарня на Wix і товариство, у якого телефон стоїть на всіх девʼяти
  сторінках, отримували «немає сторінки Contact». Це не просто хибне
  спрацювання, а перекіс проти класу: малий сайт кладе контакти на єдину
  сторінку замість окремої адреси. `PageSignals.body_contacts` для цього
  вже існував.
- **Три класи суджень, які виходять за доказ.** Скринінг усього каталогу
  дав 22 кандидати, з яких 11 довелося переписати. Класи повторювані, і
  варто питати про кожен новий текст:

  1. **Чужа поведінка.** «Google і ChatGPT не зараховують», «вас не
     називають», «пошукові системи роблять висновок». Ми не питаємо ані
     ChatGPT, ані Google і не спостерігаємо, що вони роблять.
  2. **Поведінка відвідувача.** «людина піде», «клієнт іде до
     конкурента», «гроші витрачено, а замовлення немає». Ми не міряємо
     ані відвідувачів, ані продажі.
  3. **Категорична відсутність із часткового погляду.** «Ніде не
     сказано» після десяти прочитаних сторінок із пʼятдесяти.

  Лишається те, що ми справді бачили, і механізм, задокументований
  специфікацією чи поведінкою браузера. Заборона в robots.txt категорична
  правомірно: сайт САМ її опублікував, і ми прочитали її на власні очі.
  А от що асистент відповість, коли не зможе відкрити сторінку, — уже
  не наше спостереження.
- **Пом'якшення в одному реченні виправдовувало твердження в іншому.**
  `tech.crawler_blocked` казав «ChatGPT і подібні сервіси не **можуть**
  прочитати ваш сайт і **не згадують вас у відповідях**». Друга частина —
  рівно та обіцянка, яку забороняє
  `test_consequence_does_not_promise_what_we_never_measured`, і вона
  роками проходила перевірку: сторож шукав пом'якшення БУДЬ-ДЕ в тексті,
  а «можуть» стосувалося першої частини. Тепер пом'якшення мусить стояти
  впритул до твердження — пом'якшена форма використовує інше дієслово
  («можуть не згадувати»), тож поруч із категоричним «не згадують» його
  просто не буває. Спіймано власником на perplexity.ai, який і читають,
  і згадують.
- **Ми бачимо свій запит, а не чужий.** Код 403 нашому агенту не
  доводить нічого про GPTBot: інший user-agent, інші правила, інший
  результат. Текст тепер описує наше спостереження, називає загальну
  закономірність закономірністю й прямо каже, чого ми не перевіряли.
- **Ми продавали спостереження, якого не виконували самі.** Власна форма
  «Контакти» стояла без `method` — тобто GET із порожньою дією, — і при
  збої скрипта поклала б імʼя, пошту й текст звернення в адресний рядок,
  в історію браузера й у `Referer`. Наш власний детектор це побачив і
  промовчав: правило вимагало ще й непорожнього `action` з міркуванням
  «форму без дії відправляє JS, method декоративний». Міркування хибне
  двічі: браузер робить GET на поточну адресу однаково, а глушило воно
  рівно той випадок, заради якого чек існує. Безпека розмітки не сміє
  залежати від скрипта, тож у форми тепер справжні `method="post"` і
  `action` на власний маршрут.
- **Захист від ботів і безпечний метод — два незалежні твердження.**
  Turnstile нічого не каже про те, куди браузер покладе поля. Форма з
  челенджем на GET мусить дати обидві знахідки, і вони мають різні
  `issue_key` — для клієнта це дві різні дії.
- **Розширення спрацювання ваговитої знахідки — теж зміна скорингу.**
  Зняття `and f.action` виміряно A/B на 50 свіжих знімках: старе правило
  не спрацювало ЖОДНОГО разу, нове — на 5 із 16 сайтів із формою заявки,
  зсув бала −2…−3, модуля tech −11…−20. Скоринг заморожений, а зняти
  заморозку — рішення власника, тож `tech.form_protection` отримав
  `weight = 0`: виявлення, докази, рекомендація і звіт працюють повністю,
  ціна лишається рішенням фази калібрування. Той самий шлях, що в родини
  hreflang.
- **Вигадана конкретика гірша за загальність.** Наслідок LCP казав
  «Головне зображення чи заголовок зʼявляються надто пізно», а доказ
  чека несе метрику, число, поріг, стратегію й джерело — і жодного слова
  про елемент. Ми ніколи не дізнаємось із власних даних, що саме є
  найбільшим елементом сторінки. Те саме звужено в `a11y.blocking`: він
  спрацьовує на восьми перевірках axe, з яких лише дві стосуються форм,
  тож текст про «оформлення замовлення» був би ширшим за доказ.
- **Мовчазний фолбек не ловиться перевіркою голого імені ключа.**
  Множинні рядки лежать у словнику з суфіксом форми (`.one`, `.other`),
  і скрипт, що шукав `free.issuesFound`, не знаходив нічого — тож
  іспанський і німецький екрани показували «41 issues found». Знайдено
  очима на живому екрані, не тестом.
- **Липка шапка в повносторінковому знімку — артефакт Chromium, не
  дефект UI.** У DOM рівно один `<header>`; повторення виникає при
  склеюванні смуг. Лікується процедура захоплення (липке знімається
  перед знімком), а не верстка. Ворота на це є, і вони не попереджають,
  а НЕ ДАЮТЬ зберегти файл: попередній пакет поїхав власнику саме тому,
  що неправильний знімок зберігся й виглядав правильним.
- **Локалізований рядок у ключі сортування дає стільки порядків, скільки
  мов.** Трійка головних проблем розводила рівний вплив першим реченням
  `consequence` — текстом мовою сторінки. Той самий аудит ka-dent.com.ua
  з двома знахідками по −3 показував їх у різному порядку: англійська й
  російська починали з телефонів, решта чотири мови — з опису сторінки.
  На фікстурі старий ключ давав три різні порядки на шість мов. Ключ
  тепер: вплив, вага серйозності зі скорингу, `rank` білдера, `issue_key`
  — жодного рядка, який читає клієнт, і четвертий крок не лишає рівності
  взагалі. Порівнювати порядок можна лише за ідентифікаторами, тож
  вибір трійки винесено в `top_recommendations()` окремо від подання.
- **Неперевірена сторінка й сторінка, що не відповіла, — різні числа.**
  Другий рядок покриття малювався з `pages_failed`, і на ka-dent.com.ua
  (10 із 52, невдач нуль) його не було зовсім: екран мовчав про сорок
  дві сторінки. Читач питає про решту знайденого, а це
  `known − read`; `pages_failed` — вужчий факт, і він лишається в
  контракті для звіту. Ключ зветься `unchecked`, а не `failed`, бо описує
  наш бюджет, а не поведінку сайту.
- **Доказ мусить витримати кожен шлях чека, а не типовий.**
  `ai.schema.contact` подавався як «адреса й години роботи є на сторінці,
  але не розмічені». Годин роботи чек не шукає взагалі; гейт `_looks_local`
  пропускає сайт із самим телефоном, тож адреси може не бути; знахідка
  сайтова, а «на сторінці» називає не ту одиницю; а в рідкісному шляху
  контакт лежить у JSON-LD чужого типу, тобто структуровані дані є — немає
  бізнес-розмітки. Кожне з чотирьох тверджень окремо здавалось дрібницею.
  Формулювання звужено до «контактні дані є на сайті, але не позначені
  структурованими даними про бізнес» — форма авторська, предмет доказовий.
- **Turnstile монтується в закритий shadow root.** Ворота захоплення
  чекали на `iframe` усередині `.cf-turnstile` і відмовили всім відкритим
  формам — при тому, що токен видавався, а звернення проходило.
  `querySelector` не бачить закритого shadow DOM ніколи. Готовність
  доводять розмір змонтованого контейнера і `data-rendered` від скрипта;
  життєвий цикл — непорожнє приховане поле `cf-turnstile-response`.
- **Звичайний віджет Turnstile — 300px, а форма на 320px вужча.**
  Автоматична перевірка ширин спіймала переповнення на 42px першим
  прогоном; знімки цього не показали б, бо контейнер просто вилазив за
  межу. Розмір обирається за шириною контейнера ДО рендеру (`compact`
  нижче за 300px): після рендеру віджет не перевбирається. Мова віджета
  теж передається явно — без `language` Cloudflare бере мову браузера, і
  українська сторінка показувала «Verification failed» англійською.
- **Ворота на мінімальний кегль стосуються абзаців на вузькому екрані.**
  Перша версія міряла кожен `<p>` на будь-якій ширині й відмовила
  десктопному знімку через 12px надзаголовка «КОНТАКТИ». Підпис блоку —
  не пояснювальний текст; межа — 640px, як у токенах шкали, і пʼять слів
  як ознака абзацу. Інакше ворота вимагають від надзаголовка розміру
  речення.
- **Два лічильники в одному доказі — це нуль доказів.** Файл доказу воріт
  починався з «збережено 0, відмовлено 0» від лічильника захоплення й
  закінчувався «6 із 6» від лічильника сценаріїв. Підсумок тепер один:
  перевірено, відмовлено, помилково збережено, результат — і кожен
  сценарій показує очікуване, фактичне й те, що файлу не створено.
- **Смужка ходу міряє одне, а аудит складається з шести робіт.** Екран
  очікування показує стадію словами й частку прочитаних сторінок — але
  смужка живе рівно доти, доки сторінки ще додаються. Після краулу та
  сама повна смужка означала б «лишилось нуль», тоді як попереду ще
  вимірювання швидкості, рендер, перевірки й бал; число сторінок стає
  доведеним фактом і подається фактом. Стадій шість, і кожну довелося
  назвати окремо саме тому, що безіменна фаза виглядає як зависання:
  до `STAGE_DISCOVERY` екран мовчав перші пʼятнадцять секунд (robots і
  карта сайту), а до `STAGE_MEASURING` завмирав на «10 з 10» на весь
  час PSI — тобто на найдовшу частину аудиту. Заради останнього
  вимірювання швидкості стало окремою задачею замість `gather`: інакше
  керування повертається аж після обох, і назвати роботу, що лишилась,
  нема коли.
- **Знаменник ходу обмежений бюджетом, а не сайтом.** Черга краулу може
  містити сотні адрес, і показати їх знаменником означало б намалювати
  смужку, яка за побудовою ніколи не дійде до кінця. `known` — це
  `min(прочитано + черга, max_pages)`.
- **Хід пишеться лише для аудиту з ОДНІЄЮ ціллю.** При кількох краули
  йдуть паралельно, і одне число описувало б то одну ціль, то іншу.
  Порожнє поле чесніше за неоднозначність, тож фронт мусить уміти стан
  «чисел ще немає» — він же й нормальний стан перших секунд.
- **Разова покупка анонімна, і «оплата спершу» не сміє тягти за собою
  реєстрацію.** Картка «Разова перевірка» на сторінці цін до 6 вересня
  2026 вела на форму безкоштовного превʼю: людина, що натиснула
  «Отримати звіт», бачила перевірку сайту, а про оплату дізнавалась
  через хвилину. Першою спробою це полагодити я повів кнопку на
  `/checkout` — і зламав інше: та сторінка при 401 відправляє на
  `/login`, тобто разовий продаж почався б із реєстрації, якої в ньому
  немає. Правильний порядок: `/buy` → каса гостя → підтверджена подія →
  адреса сайту й факти бренду → аудит і присутність → чотири документи.
  Ані користувача, ані пароля на цьому шляху не створюється ніде.
- **Хто купує анонімно — це організація без учасників.** Гостьова сесія
  (`POST /v1/public/sessions`) не потребує ані аудиту, ані акаунта, а
  `one_off_purchases.audit_id` nullable — тож покупка може існувати до
  того, як людина назве сайт. Звʼязок «покупка → аудит» ставиться в
  момент, коли вона його називає, і там же відкривається повний вигляд:
  підстава — власний запис зі статусом PAID, а не довіра до браузера.
- **Спроможність гостя живе на вкладку, а оплачена покупка — ні.** Токен
  лежить у `sessionStorage` (для превʼю це правильно: закрив вкладку —
  нічого не втратив), але для оплаченої покупки те саме означало б
  втрату грошей. Тому замовлення (номер покупки + токен) дублюється в
  `localStorage`, і людина, що заплатила й закрила вкладку, повертається
  на `/buy` і продовжує. Правом це не є: сервер однаково звіряє покупку
  з організацією токена.
- **Каса воронки не несла умов пропозиції — і продавала половину
  продукту.** `open_checkout` створював покупку без `offer_code` і без
  зліпка, тож `_grant_for` падав у фолбек «quantity аудитних кредитів» і
  видавав НУЛЬ перевірок присутності. Панель присутності на оплаченому
  екрані через це не могла запуститись ніколи — при тому, що присутність
  входить у разову покупку. Обидві воронки тепер відкривають ту саму
  пропозицію каталогу, і видача приходить її зліпком.
- **Закрите вікно каси — не «оплата не пройшла», і не «все гаразд».**
  Три різні відповіді жили під одним текстом: провайдер підтвердив
  «не оплачено», провайдер мовчить, і відмовили ми самі (429 від
  обмежувача частоти). Усі три казали «Кошти не списано. Можна
  спробувати ще раз», а кнопка при цьому перезавантажувала ту саму
  адресу — тобто не робила нічого. «Кошти не списано» має право сказати
  лише перший стан; другий каже «підтвердження ще немає»; третій —
  «забагато спроб» і кнопки не показує взагалі, бо вона привела б у ту
  саму відмову.
- **Обмежувач частоти рахує запити, а не роботу.** Десять на годину на
  адресу — норма для дій, кожна з яких додає роботи. Але «відкрити касу»
  після `reuse_pending` віддає ТУ САМУ покупку й ту саму транзакцію,
  тобто не створює нічого, і спільна десятка означала б, що людина, яка
  двічі закрила вікно оплати, не може заплатити ще годину. Скільки кас
  узагалі заведе одна адреса, обмежує ліміт на відкриття гостьової
  сесії. Лічильники живуть у Redis і переживають перезапуск API — на
  цьому я двічі згаяв час, шукаючи дефект у коді.
- **Мертвий токен гостя робить кнопку вічно зламаною.** Спроможність
  живе сім днів, а `ensureGuestSession()` віддавала те, що лежить у
  сховищі, не питаючи сервера. Протухлий (чи чужий) токен давав 404 на
  кожен запит, і повторне натискання било в ту саму стіну. Тепер 404 на
  відкритті каси означає «перед нами новий відвідувач»: сесія
  переоформлюється, і оплата йде далі.
- **Памʼять браузера не сміє перехоплювати свіжий візит.** Замовлення
  лежить у `localStorage`, щоб оплачена покупка пережила закриту
  вкладку. Але поки будь-яке памʼятане замовлення підхоплювалося на
  вході, людина зі сторінки цін потрапляла не в касу, а в очікування
  чужої покинутої покупки — і бачила «оплата не пройшла» ще до того, як
  щось натиснула. Памʼять читається лише тоді, коли покупка справді
  жива: оплачена або вже витрачена на аудит.
- **Оплачено, але перевірку не запущено — третій стан, і його не бачив
  ніхто.** Він не «незарахована оплата» (кредити видані) і не «доступ не
  видано» (аудиту ще немає), тож жоден перелік адмінки його не показував.
  Перемикач «Оплачені без перевірки» на екрані оплат показує саме його —
  і лише для гостьових організацій: у кабінеті покупка без аудиту це
  нормальне поповнення балансу.
- **Дві куплені одиниці — два незалежні числа.** Пакет продає перевірки
  й присутність окремими кількостями (рішення власника 2026-09-06): вони
  й списуються окремо (`credit_type`), тож продавати їх одним N означало
  б обіцяти те, чого в пакеті може не бути. Разова лишається 1 + 1 за
  означенням формату.
- **Смужка й відсоток — те саме твердження, лише намальоване.** У
  загальному звіті присутності бала немає навмисно: зведене число
  обіцяло б «видимість», якої ми не міряли. Замість нього дві дроби, і
  відсоток поруч зʼявляється лише тоді, коли його порахував двигун
  метрик (`MIN_OBSERVATIONS_FOR_RATE`) і коли чисельник не нуль: «0%»
  біля «0 / 96» — третє повторення того самого нуля. Смужки немає саме
  тому, що вона обійшла б цей поріг мовчки.
- **Число з іменником вимагає чотирьох форм множини на шість мов.**
  «42 відповіді», «58 відповідей», «21 відповідь» — і те саме в
  німецькій, іспанській, французькій. У переліках загального звіту
  присутності стоїть голе число, а що воно означає, каже підпис під
  списком: одне речення замість двадцяти чотирьох форм.
- **Знаменник, менший за покриття, читач помітить.** Прогін дав 237
  придатних відповідей, а згадки рахуються з 96: у метрику входять лише
  запитання, які не називали бренд. Поки цього не сказано вголос,
  документ виглядає так, ніби загубив дві третини даних.
- **Покриття має стояти поруч із балом, а не в доказах.** `asana.com` —
  20 адрес із 3407 і бал 59, поданий так само впевнено, як бал за сайтом,
  прочитаним повністю. Тепер `summary.coverage` несе прочитано /
  завантажено / не відповіли / відомо. Числа беруться з `evidence`, а не
  з нових полів: обидва шляхи збірки звіту вже їх несуть, і третє місце
  зберігання того самого факту тільки розійшлося б із першими двома.

- **Стеля повторень довго міряла детектор, а не проблему.** Вона рахувалась
  на `code`, а один код тримає кілька різних проблем: під
  `perf.core_web_vitals` живуть LCP, INP, CLS і TTFB. При критичній метриці
  (вага 4 × 5 = 20 при стелі 20) друга провалена метрика коштувала рівно
  нуль — сайт з однією й сайт із трьома отримували ті самі 60 балів модуля.
  На calendly.com це були LCP 5204 мс та INP 652 мс, обидві критичні.
  Тепер стеля рахується на `issue_key`, а чеки оголошують `variants`.
  Перерахунок 35 знімків: зсунувся 21 сайт із 29, медіана −1, максимум −4,
  усі вниз; преміювання бренду й ширина діапазону не змінились.
- **Ключ каталогу — не ідентифікатор.** Групувати рекомендації за `msg`
  давало правильний поділ із неправильної причини: рядок каталогу
  перейменовують разом із текстом, і редагування формулювання мовчки
  зсувало б бали. Тому поділ оголошується окремо (`Check.variants`), а не
  виводиться з повідомлень.
- **Два повідомлення інколи описують одну проблему.** «Бракує кількох
  заголовків безпеки» проти «немає жодного», «сторінка важка» проти
  «сторінку не дочитали», «розмітки немає ніде» проти «є не всюди» — це
  ступені одного дефекту, і спільна стеля для них правильна. Критерій:
  чи виправляються вони одним і тим самим редагуванням. Таких чеків шість,
  і `variants` вони не оголошують.
- **Відбиток скорингу не бачить змін логіки.** `scoring_version()` хешує
  константи — ваги, півшкали, стелі, множники. Перехід стелі з `code` на
  `issue_key` не зачепив жодної константи, але зсунув бали всієї вибірки.
  Тому поруч стоїть ручний `SCORING_RULES`: його піднімає той, хто змінив
  саме правило підрахунку.
- **Відбиток детектора не бачить змін умови — і це вже дало колізію.**
  `detector_version()` хешує ОГОЛОШЕННЯ чеків: код, модуль, серйозність,
  вагу, зусилля, варіанти. Умову всередині `run()` він не бачить. Коли
  `get_method` перестав вимагати непорожнього `action`, а потім вага
  повернулась із 0 у 3, відбиток збігся з `e3f7e1172d70` — детектором,
  який цієї знахідки не видавав жодного разу. Два різні детектори під
  одним іменем. Звідси ручний `DETECTOR_RULES` поруч зі `SCORING_RULES`.
- **Для важкої знахідки повторення досі коштує нуль, і це не про K4.**
  Друга стеля (0.5 півшкали) нижча за одну критичну знахідку Core Web
  Vitals: 15 проти 20, тож `max(worst, ceiling)` згортається до самої
  знахідки. Двадцять сторінок із поганим LCP коштують як одна. Це
  властивість взаємодії двох стель, вона існувала й до поділу на
  `issue_key`, і виправляти її означає рухати параметри шкали. Зафіксовано
  тестом `test_a_heavy_problem_repeated_is_clamped_by_the_module_ceiling`,
  щоб наступна зміна параметрів побачила її явно.

- **Організація разової покупки не шукається через покупця.** Анонімна
  воронка не має ані акаунта, ані відображеного клієнта: Paddle створює
  свого в касі, і його ідентифікатор ми бачимо вперше в події оплати.
  Поки `_organization_for` викликався до розвилки, кожна справжня
  оплата гостя падала б на «не знаємо, чия це подія» — тобто гроші
  проходили б, а доступу не було б. Джерело — наш власний запис
  покупки; питання «чия подія» лишилось там, де запису немає.
- **«Не слухаємо» і «відхилено» — різні відповіді провайдеру.**
  `UnhandledEvent` навмисно НЕ підклас `InvalidWebhook`: перше вимагає
  200 (інакше Paddle повторюватиме `subscription.*` вічно), друге —
  400. Один тип на два стани — та сама помилка, що колись дала один
  `scope` для «жодної сторінки» і «рівно одна».
- **Друга транзакція під той самий намір — це друге списання.** Дві
  вкладки, дві каси, один наш ідентифікатор у довільних даних обох.
  Мовчазне поглинання виглядало б ідемпотентністю, а насправді людина
  заплатила двічі при одному рядку: повертати зайве нема за чим, а
  повернення єдиної покупки забирає доступ, оплачений двічі. Друга
  оплата стає власною покупкою на той самий аудит.
- **Невдала оплата не має бути станом покупки.** Термінальне «не
  оплачено» перетворює відмову банку на блокувач: людина мусить чекати
  на нашу дію, щоб спробувати ще раз. Покупка лишається PENDING, а
  «оплата не пройшла» екран бере з журналу подій.
- **Фейковий провайдер у проді — це безкоштовний платний звіт.** Він
  приймає будь-який вебхук із `x-fake-signature: valid`. При
  `app_env=prod` він не реєструється взагалі, і гейт стоїть у реєстрі,
  а не в маршруті: через реєстр проходять і каса, і вебхук, і те, чого
  ще немає.
- **Поріг ціни живе в прайсі провайдера, а не в коді.** Тест обходить
  `app/` і падає на будь-якому `pri_…`: інакше зміна ціни ставала б
  релізом, а перехід на іншого провайдера — правкою домену.

- **`checkout.url` у Paddle — це адреса каси, а не адреса повернення.**
  Поки ми клали туди своє «повернення», кожна транзакція мовчки
  перекривала обліковий default payment link сторінкою, якої не існує:
  помилки немає, посилання просто веде в нікуди. Поля `return_url` у
  контракті більше немає саме тому — його нікуди покласти. Куди йти
  після оплати, вирішує `successUrl` у Paddle.js, тобто браузер.
- **Сторінка default payment link ініціалізує Paddle.js на завантаженні,
  а не на кліку.** У цьому вся її суть: побачивши `_ptxn`, Paddle.js
  відкриває касу сам. Сторінка, що ініціалізує провайдера в обробнику
  кнопки, виглядає робочою й для цього шляху не працює взагалі — і
  `/result` без `?audit=` показала б покупцеві форму замість каси.

- **Шар, який «нічого не робить», лишається без тестів — і саме там тече.**
  `report/web.py` лише перекладає внутрішнє представлення в публічний
  контракт, тож його ніхто не покрив. За цей час у контракт просочилися
  дві речі: виключений модуль віддавав бал `0` замість `null` (усередині
  `ScoreEntry.score` — int, і нуль там службовий, docx щоразу обходить
  його перевіркою `excluded`), а приписка до прогалини даних була зашита
  українською й потрапляла в англійський звіт. Тест на `note` існував,
  вимагав українського рядка в звіті мовою за замовчуванням і тим
  закріплював помилку замість того, щоб її ловити.
- **«+0 до бала» — найгірший із можливих підписів.** Він каже, що дія не
  варта нічого. Нуль означає одне з двох, і жодне з них не «марно»: або
  приріст менший за одиницю після округлення, або загального бала немає
  й рахувати немає від чого. На заблокованому сайті друге давало «+0»
  біля пункту «пустіть краулерів» — найціннішої дії в переліку.
- **Заголовок знахідки — не дамп провайдера.** `LCP = 4126.042ms` обіцяє
  точність до мікросекунди там, де величина гуляє на сотні мілісекунд
  між вимірюваннями. Заголовок читає людина, доказ читає інструмент:
  `_for_reading` формує `4.1 s` і `344 ms` для `params`, точне значення
  лишається в `evidence`. Одиниця йде з нерозривним пробілом — число,
  відірване переносом рядка, читається як інше число.
- **Макет із вигаданих даних не перевіряє екран.** Знахідки для екрана
  звіту зібрані зі знімків реальних сайтів тим самим шляхом, що й у
  продукті (`знімок → rescore → build_report → to_web`). Вигаданий макет
  за побудовою не має ані пріоритету з нульовою кількістю сторінок (бо
  проблема стосується сайту цілком), ані доказу на вісім полів, ані
  заголовка на два рядки — і саме тому виглядає бездоганно.
- **Меню, притиснуте до низу екрана, не може розкриватися вниз.** Обліковий
  запис стоїть унизу липкої бічної панелі, тож `Dropdown` там відкривається
  вгору (`side="up"`). На короткій сторінці дефект маскувався скролом,
  на довгому звіті меню виходило за межу вікна цілком. Знайдено тим, що
  Playwright не зміг клікнути пункт меню.
- **Паритет мов сліпий до ключа, якого бракує всім.** Тести порівнюють
  мови між собою, тож `area_accessibility` і `verdict_unknown`, відсутні
  в усіх шістьох каркасах одразу, проходили всі перевірки — а клієнт
  бачив у таблиці сирий ключ. Знайдено лише розгляданням згенерованого
  Word-документа очима (docx → Word COM → PDF → перегляд сторінок);
  тепер `test_report_locale_parity` шукає сирі ключі в `document.xml`
  обох фікстур, бо `verdict_unknown` живе лише в документі без бала.
- **Кластер і причина — різні твердження.** Пілот на пʼяти сайтах дав 34
  групи, і причина була доведена рівно в чотирьох: там, де знахідки
  говорили про те саме значення або ту саму відповідь сервера. Решта
  тридцять були корисними кластерами з правдоподібним припущенням — бо
  контракт вимагав поле `hypothesis` завжди, і модель мусила вигадати
  причину, щоб заповнити схему. Найяскравіше на трьох групах
  доступності: кластер справжній, а причина трималась лише на тому, що
  знахідки прийшли з одного запуску Lighthouse. Спільний інструмент
  вимірювання не є спільною причиною, і `cause_confidence: unknown` —
  правильна відповідь, а не поразка.
- **Модель не може поважати межі, яких їй не показали.** На
  gocplumbing.com вона написала «site-wide», прочитавши 3 сторінки з 10.
  Двигун при цьому прямо казав «7 з 10 адрес не відповіли» — але
  покриття не входило у вхід задачі. Це був дефект нашого входу, а не
  моделі: перш ніж вимагати обережності, треба передати факти.
- **Впевненість губиться на межі задач, якщо вона не поле.** Групування
  помʼякшувало висновки правильно, а план виправлень ті самі висновки
  подавав категорично: «X and Y ARE THE UPSTREAM CAUSES» при джерелі
  `likely`. Усі шість категоричних фраз пілота знайшлися в планах,
  жодної в групуванні. Лікується стелею на `causal_basis`, а не
  чорним списком фраз: продукт працює шістьма мовами, і «caused by» не
  побачить ані німецького «verursacht durch», ані українського
  «спричинено».
- **Детектор вигаданих сум ловив ціни клієнта.** `$0` і `$1` у
  розумінні linear.app були тарифами з їхньої ж сторінки цін. Грошова
  величина тепер звіряється з поданим входом: є в джерелі — цитата,
  немає — вигадка. Решта шаблонів (години, гарантії) джерелом не
  виправдовуються ніколи.
- **Два AI-шари, і плутати їх не можна.** `app/audit/llm/` стоїть ДО
  скора й уміє створити знахідку (`llm.unstated_facts`), тобто змінити
  бал; `app/enrich/` стоїть ПІСЛЯ правди аудиту й не має шляху назад.
  Спільного коду між ними немає навмисно — інакше новий шлюз міг би
  випадково активувати старий шлях, який досі не звірявся з
  детерміністичною правдою.
- **Рендер звіту не ходить у мережу.** Виняток був один — `?enrich=true`
  на owner-docx, — і в нього був дефект: результат ніде не зберігався,
  тож кожне повторне завантаження того самого файлу коштувало нового
  платного виклику. Тепер маршрут просить розширення з `enabled=False`,
  і це структурна межа, а не наслідок вимкненого `llm_enabled`.
- **Ідентичність збагачення — це індекс, а не дисципліна.** «Оновлення
  сторінки не купує другий виклик» тримається на UNIQUE (аудит, задача,
  версії, хеш входу), тож гонка двох перших запитів вирішується базою.
  Локаль входить у хеш: інша мова — інший артефакт, а не перезапис.
- **Стан із бази, а не з мапи ідентичності.** Перевірка «чи не змінився
  вхід аудиту з моменту постановки» читає аудит наново, і без
  `populate_existing=True` вона відповідала закешованим обʼєктом —
  тобто завжди «не змінився». Тест ловив це видаленням знахідки.
- **Знімок, зроблений до появи поля, не бачив нічого — і не має свідчити.**
  Чек «сайт віддає сторінки різними мовами й не оголошує версій» спрацював на
  MDN і FastAPI при перерахунку benchmark-знімків: не тому, що в них немає
  hreflang, а тому, що знімки старші за саме поле. Порожнеча там описує нас.
  `SiteContext.hreflang_observed` розводить «дивилися й не знайшли» від «не
  дивилися»; `snapshot.load` ставить `False`, коли в збережених сторінках немає
  самого ключа. Той самий клас, що й «твердження про відсутність вимагає, щоб ми
  там дивилися», але цього разу прогалину створив наш власний формат зберігання.
- **Одна правка не має коштувати трьох стель.** На fastapi.tiangolo.com усі
  тринадцять мовних версій позначені `hreflang="en"` — одна помилка шаблону. Вона
  запалювала три різні `issue_key` (суперечність, немає самопосилання, немає
  зворотних посилань). Виправлено не вагами, а логікою: набір, який Google може
  відкинути цілком, не можна судити на повноту — поки суперечність не усунуто,
  відповіді про взаємність просто немає звідки взяти. Поділ на `variants`
  лишився правильним; проблемою був збіг варіантів від одного кореня.
- **«Не стиснув» — твердження про нас, поки не сказано, що ми просили.**
  httpx надсилає `Accept-Encoding: gzip, deflate`, бо пакетів `brotli` і
  `zstandard` в оточенні немає. Сервер, який уміє лише Brotli, віддасть нам
  identity — і назвати це «сайт не стискає» було б неправдою про сайт, зате
  правдою про нашу установку. Тому `accept_encoding` зберігається поруч із
  відповіддю, а формулювання завжди про відповідь, а не про сервер.
- **Довжина тіла — це розпакований розмір, а `Content-Length` — переданий.**
  httpx розпаковує сам, тож на python.org тіло 52 908 байтів при
  `Content-Length` 11 631. Це різні величини; ділити одну на одну можна лише
  коли обидві є і немає `chunked`. Коли впевненості немає, розмір лишається
  `None` — вигаданий відсоток економії гірший за його відсутність.
- **Умова знахідки має описувати світ, а не контраст у межах прогону.**
  Знахідку про HTTP/1.1 я спершу вмикав, лише якщо в тому самому аудиті були й
  HTTP/2-відповіді. Це мовчало б рівно на тому сайті, який усюди віддає
  HTTP/1.1, — тобто на єдиному справжньому випадку. Доказ того, що межа не наша,
  дає конфігурація клієнта (`h2` встановлено, `http2=True`), а не сусідні
  сторінки. Той самий клас помилки, що й `frontier is None` у краулі.
- **Спільний вміст стирає сам себе, якщо рахувати частоту за сторінками.**
  Обвʼязка визначається як «шинґл, що трапляється на багатьох сторінках», і три
  однакові сторінки з чотирьох — це 75%: їхній спільний текст оголошувався
  шаблоном і зникав саме тоді, коли він і був знахідкою. Частота рахується за
  **різними вмістами**, а не за сторінками, і поріг має абсолютний мінімум у три:
  на сайті з трьох сторінок частка 0.6 дає поріг два, тобто пару дублікатів.
- **Поріг подібності на `<body>`-тексті міряє навігацію, а не сторінки.**
  `PageSignals.text` — це `<main>`, а без нього весь `<body>`, тобто разом із
  меню й бічною панеллю. Фільтр обвʼязки це рятує лише поки сайт одномовний: на
  fastapi.tiangolo.com англійська панель трапляється на двох сторінках із
  двадцяти чотирьох (решта — інші мови), тож фільтр її не впізнає, і дві майже
  порожні сторінки дали 0.944. Тому близькі дублікати вимірюються, але знахідкою
  не стають: точний збіг порога не потребує, а поріг без виділення головного
  вмісту — це вимірювання чужої величини.
- **Дублікат і однаковий каркас — різні речі.** Чотири адреси SPA віддають той
  самий скелет, і за текстом вони ідентичні. Це не дублікати сторінок, а
  відсутність сторінок. Межа власного вмісту (скільки шинґлів лишилось після
  чистки) розводить ці випадки; на вибірці саме вона прибрала auditlensapp.com.
- **Браузер підвищує схему до того, як спрацює подія запиту.** Журнал
  `page.on("request")` на всій вибірці показав рівно один сайт із `http://` і
  жодного `ResourceLoad` — не тому, що сайти чисті, а тому, що Chrome переписує
  придатні запити раніше. Отже, змішаний вміст доводиться шукати в розмітці, а
  журнал браузера лишається підтвердженням, а не джерелом. Хто збереже лише
  спостережене, побачить нуль там, де насправді вісім скриптів.
- **`third_party_hosts` втратив схему, і питання не мало відповіді.**
  Екстрактор обходив `script[src]`, `link[href]`, `iframe[src]` — і зберігав
  самі хости. Тобто «чи є на сайті змішаний вміст» із розмітки не було як
  дізнатися взагалі, хоч усі теги перед нами й проходили. Тепер незахищені
  адреси зберігаються цілими, і лише коли сама сторінка на https.
- **Заявлене й спостережене — два різні твердження.** «Ресурс заблоковано» без
  побаченого блокування — вигадка; «все гаразд, браузер підвищить схему» —
  вигадка навпаки, бо підвищення живе рівно доти, доки існує https-версія
  файлу. Тому `handling` (очікуване за специфікацією) і `observed` (побачене в
  журналі) лежать поруч і ніколи не підміняють одне одного, а сторінка, яку не
  рендерили, чесно каже `no_render`.
- **Екстрактор лишає перше посилання на адресу — і це ховає текст.** У картці
  першим стоїть зображення без `alt`, а підпис — у сусідньому `<a>` на ту саму
  ціль; другий `<a>` відкидається дедуплікацією, і до нас доходить порожній
  текст. Чек «порожній текст посилання» через це спрацьовував на 524 посиланнях
  aldg.org (третина всіх контекстних) і 240 crustula (дві третини). Це наша
  сліпота, а не дефект сайтів, тож клас не випущено взагалі: число лишилось у
  покритті, а знахідки з нього немає. Полагодити можна лише зміною дедуплікації,
  а вона рухає пріоритет краулу й два ваговиті чеки.
- **Поріг має збігатися з твердженням, а не з бажаною кількістю спрацювань.**
  Підпис «дізнатися більше» на одну сторінку — питання стилю; двозначним він
  стає рівно тоді, коли за ним ховаються різні адреси. Тому чек про текст
  посилань спрацьовує від двох різних цілей на фразу, і це не підібране число, а
  умова, за якої твердження стає правдою. Порогу для «задовгого» тексту ми не
  знайшли — тому чека про довжину немає взагалі.
- **Граф знав «вісім посилань», але не знав жодного з них.** `LinkRef` несе
  текст посилання з самого початку, відрендерені посилання лежать у
  `RenderResult.signals.links`, а доказ про зламані адреси був пласким
  `{адреса: "HTTP 404"}`. Бракувало не збору, а зʼєднання: клієнт отримував
  перелік поламаного без жодної згадки, де це полагодити. Спостереження живуть
  тепер в `link_evidence.py` окремо від поламаності — наступному пункту про
  якість тексту посилань потрібні рівно вони.
- **Доказ у Word їхав сирим `repr` словника.** `_format_evidence` рендерив
  будь-який список через `str(v)`, і вкладена атрибуція потрапляла в документ
  клієнта як `{'from': '…', 'in_chrome': False}` — з лапками й `False`. Поки
  докази були пласкі, це не було видно. Тепер формат обмежений глибиною, а
  залишок згортається в `(+N)`: урізане не має вдавати повне.
- **Розширення файлу не відповідає на питання про схему.** Карта змішує
  сторінки з картинками, бо `root.iter()` збирав кожен `loc` на будь-якій
  глибині; на crustula.com.ua пʼять зниклих світлин виглядали як пʼять зламаних
  сторінок. Першим фіксом я відсіяв їх за розширенням — і це неправильне
  розрізнення: у картинки розширення може не бути (`/render/1024`), можуть бути
  параметри (`/img?id=7`), вона може лежати на чужому домені, а `/report.pdf`
  усередині `<url><loc>` — цілком справжній документ сайту. Схема ж каже точно:
  `<url><loc>` — це запис, `<image:image><image:loc>` — його ресурс. Розбір
  тепер структурний, а фільтр розширень лишився тільки як сумісність зі
  знімками, знятими до цієї правки.
- **Один прочитаний файл індексу — не погляд на карту.** `collect_sitemap` брав
  `urls[0]` і не рахував, скільки дітей існує. На crustula.com.ua це давало 21
  «адресу», з яких десять не були сторінками, — а сам `/sitemap.xml` виявився
  індексом, якого плаский розбір не впізнавав узагалі. Тепер читається до пʼяти
  дітей рівномірно по індексу (та сама причина, що й у `_spread` для адрес), і
  модель окремо несе `children_total`, `children_read` та `index_complete`:
  вибірковий погляд не сміє звучати як висновок про всю карту. Той самий сайт
  після правки: індекс упізнано, 5 дітей із 5, 86 справжніх сторінок.
- **Фікстура з `noindex` ховає причини, слабші за нього.** Синтетичний контекст
  для карти сайту я зібрав на `BAD_HTML`, а він сам несе `noindex` — і два
  варіанти з пʼяти не спрацьовували ніколи, бо `noindex` у пріоритеті вищий.
  Модель була права, помилялася фікстура. Коли чек упорядковує причини за
  вагою, фікстура мусить давати кожній причині чисту сторінку.
- **`Location` буває відносним, і ланцюг треба розвʼязувати покроково.**
  Ми зберігали значення заголовка як є, а httpbin віддає `/relative-redirect/2`
  — і це звичайна практика, не виняток. Перший крок розвʼязується відносно
  запитаної адреси, кожен наступний — відносно попереднього; без цього доказ
  показує шлях без домену, і клієнт не розуміє, куди його вели.
- **Сирі стрибки перенаправлень — не те саме, що переходи.** `/a` → `/a/` — це
  нуль змістовних кроків: обидві адреси нормалізуються в одну сторінку.
  Рахувати сире означало б вигадати клієнтові складність і відправити його
  правити те, що не зламане. Довжина ланцюга рахується в нормалізованих
  адресах, як і все інше в цьому проєкті.
- **Петлю перенаправлень довести неможливо, і це треба сказати вголос.**
  httpx кидає `TooManyRedirects` на шостому кроці й історії не віддає: ми не
  знаємо ані де крутилося, ані чи крутилося взагалі. Тому `repeated` описує
  рівно побачене — адреса трапилась двічі в ланцюзі, який завершився, — а
  `limit` каже лише «до кінця не дійшли» і слова «петля» не містить у жодній
  із шести мов. Розрізняти їх довелося структурно: `redirect_limit_exceeded`
  на `FetchResult`, бо єдина альтернатива — розбирати англійський рядок
  чужої бібліотеки, щоб зробити з нього твердження для клієнта.
- **Умова «чи передали параметр» — не те саме, що «чи це перший раз».**
  Краул почав викликатися хвилями, і те, чи брати завантажену наперед головну
  сторінку, я вирішував через `frontier is None`. Черга ж передається завжди,
  тож у кожному справжньому аудиті головна мовчки зникала: excalidraw.com дав
  0 сторінок і 0 помилок. Усі 1494 тести були зелені — фікстури передавали
  `prefetched=None`, тобто перевіряли комбінацію, якої в продукті немає.
  Побачив живий прогін. Питання, яке варто ставити кожній такій умові: чи
  описує вона стан світу, чи форму виклику.
- **Запис походження не має замовляти запит.** `Frontier.offer()` фіксує
  джерело навіть для вже відомої адреси — і водночас ставив її в чергу. Назвати
  щойно завантажену головну сторінку означало завантажити її вдруге. Тепер
  прочитане в чергу не повертається: перевірка на `_fetched`, а не лише на
  `_seen`.
- **Бюджет рендеру виявився паливом хвиль, і це вийшло само.** Статичний сайт
  витрачає всі три рендери на першій хвилі й нічого не відкриває — бо там нема
  чого відкривати. SPA має на першій хвилі одну сторінку, тож паливо лишається
  саме там, де воно потрібне. Другий бюджет заводити не довелося: сторінки,
  знайдені через рендер, витрачають ті самі `max_pages`.
- **Заморожений скоринг — про поведінку, а не про файл.** Я доводив, що база
  не змінилася, бо `scoring.py` і `SCORING_RULES` не чіпав. Це неправда:
  ваговиті чеки змінюють бали й без правки формули. Той самий
  fastapi.tiangolo.com мав 62 до релізу й 53 після, не змінившись ані на
  байт, — два аудити по різні боки випуску стали б непорівнянні, тобто саме
  те, від чого заморозка й захищає. Родина hreflang тепер `INFO` з вагою 0,
  як `seo.render_delta`: виявлення, докази, рекомендації й звіт працюють
  повністю, а ціна — рішення фази калібрування. Перевірено на 56 знімках
  вибірки: жодного зсуву бала.
- **Список «поширених кодів» — не реєстр.** ISO 15924 я спершу вніс добіркою
  на 39 кодів письма, вибраних на око. У реєстрі їх 226, і серед відсутніх
  були цілком робочі `Aran` (насталік), `Tfng`, `Bopo`, `Java`, `Sund`:
  клієнтові, який написав правильний `ur-Aran`, ми сказали б, що значення
  недійсне. Хибне спрацювання на коректній розмітці дорожче за пропущену
  знахідку. Тепер це вендорований знімок реєстру з джерелом, датою правки й
  розміром, а `registry_problems()` падає на мовчазному усіченні. Те саме
  питання варто ставити кожному переліку в `standards/`: звідки він і за
  яким правилом повний.
- **Валідатор мусить знати граматику, яку перевіряє.** Google приймає в hreflang
  не BCP 47 цілком, а `language[-script][-region] | x-default`, і письмо за ISO
  15924 там першокласне: `zh-Hant`, `zh-Hans`, `zh-Hans-US` — приклади з його ж
  документації. Валідатор «мова + регіон», написаний від руки через відсутність
  пакета, відкинув би всі три як помилку — тобто перетворив би правильне
  налаштування на знахідку.
- **Поріг і значення мусять ділити одиницю.** Шаблон каталогу —
  `{threshold}{unit}`, і коли `_for_reading` перевела значення в секунди,
  поріг лишився в мілісекундах: «LCP = 4.1 s … поріг 2500 s» — неправда
  в тисячу разів. Той самий клас, що й «+0 до бала»: рядок складається з
  частин, які ніхто не читає разом.
- **Тест, який проходить проти власної вигадки, не перевіряє нічого.**
  `FakeOutcome` у тестах бенчмарку мав поле `status`, якого справжній
  `AuditOutcome` не має: 38 тестів були зелені, а живий прогін упав на
  першому ж сайті. Полагоджено не підгонкою фейка, а його видаленням —
  тест будує справжній `AuditOutcome`. Той самий клас, що й `frontier is
  None`: перевірялася комбінація, якої в продукті немає.
- **Глобальний стан у тестах мусить мати шлях назад.** Гард платних
  викликів підміняє `anthropic` і `openai` у `sys.modules` — для прогону
  корпусу це задум, для вибірки тестів пляма: усе, що після них
  імпортувало справжній SDK, отримувало заглушку, і 23 тести падали. Кожен
  файл окремо лишався зеленим, тож точковий прогін дефекту не бачив
  узагалі. Звідси `guard.restore()` і **автоматична** фікстура: надія, що
  наступний тест згадає прибрати за собою, вже не справдилася.
- **Два різні «benchmark», і файл тестів у них один.** Тести
  калібрувальної інфраструктури лягли в `tests/test_benchmark.py`, де вже
  жили тести `app/report/benchmark.py` — порівняння клієнта з
  конкурентами. Одинадцять тестів продуктової фічі зникли, і **вибірка
  лишилась зеленою**: зникли й самі тести, тож рахувати стало нічого.
  Побачив `git status` перед комітом — файл стояв як `M` там, де мав бути
  `A`. Звідси `tests/test_calibration_benchmark.py` із довгою назвою.
  Зелений прогін не доводить, що покриття на місці; він доводить, що
  вцілілі тести проходять.
- **Журнал рахує спроби, аналіз рахує сайти.** Повторений сайт лежить у
  результатах двічі, і зведення по рядках показувало «8 рядків, 5
  успішних, 3 збої» на корпусі з шести. На тисячі сайтів з повторами це
  завищило б частку збоїв рівно на кількість повторів. Обидві величини
  потрібні: журнал показує нестабільність вимірювання, аналіз — стан
  корпусу; змішувати їх не можна.
- **`truncate` тримає ширину сторінки, і `min-width: 0` цього не лікує.**
  Головна давала 57px горизонтального переповнення на 320px через назву
  прикладу звіту в `truncate` (`white-space: nowrap`). Мінімальна ширина
  flex-контейнера рахується з ПОВНОЇ ширини нерозривного тексту, і ані
  `min-width: 0`, ані `flex: 1 1 0` на самому тексті цього не змінюють —
  вони дозволяють стискатись елементу, а не зменшують внесок у
  min-content батька. Картка не стискалась, колонка сітки героя росла
  понад вікно. Доведено бісекцією (ховання вузлів по черзі) і трьома
  варіантами правки в живому DOM ДО зміни коду: лише дозвіл перенести
  текст (`sm:truncate`) прибирає переповнення. Ховати його через
  `overflow-x: hidden` на оболонці заборонено тестом.
- **`checkout.closed` не доводить, що грошей не взяли.** Каса закривається
  і після оплати (сама), і без неї (людина), і коли подія `completed`
  загубилась. Екран, що на саме закриття казав «кошти не списано»,
  пропонував другу оплату тому, хто зробив першу. Тепер закрите вікно —
  питання до сервера: він звіряє транзакцію з провайдером
  (`settlement_of`, `GET /transactions/{id}` у Paddle), і лише відповідь
  «не оплачено» відкриває стан із повторною спробою. Провайдер, який не
  відповів, — це `UNKNOWN`, а не «ні»: сказати «не списано» на підставі
  тайм-ауту означало б продати другу покупку за перші гроші. Права звірка
  не дає ніколи — його й далі дає лише перевірена подія.
- **Перезбірка під живим `next start` ламає сторінку мовчки.** Сервер
  тримає маніфест збірки з моменту старту, а `npm run build` замінює
  файли чанків на диску: браузер просить старе імʼя й отримує 400, тож
  гідрація не відбувається взагалі. Виглядає це як порожня сторінка без
  жодної помилки в `pageerror` — саме так `/report/{token}` «зник» на
  пів години перевірки. Ознака в консолі: `ERR_ABORTED` на
  `/_next/static/chunks/…`. Після кожної збірки сервер перезапускається.
- **Сервер, проти якого міряєш, може бути старою збіркою.** На :3000 стояв
  `next start` із попередньої сесії, і після правки `ScorePreview`
  вимірювання показувало ті самі 357px — HMR у production-сервера немає.
  Перш ніж вірити «правка не спрацювала», подивись, що саме слухає порт
  (`Get-CimInstance Win32_Process`). Те саме з API на :8000: uvicorn без
  `--reload` виконував код до правок білінгу.
- **Посилання на гостьовий екран несло мову лише для української.** `ctaOf`
  віддавав `/result?lang=uk` і голий `/result` для решти мов, форма героя на
  головній передавала `lang` лише в `uk.tsx`, а сторінка оплати впізнавала із
  сесії саме рядок `"uk"`. Гостьовий екран при цьому давно існував шістьма
  мовами: німець із німецької сторінки отримував англійський результат не
  тому, що даних не було, а тому, що адреса їх не просила. Умова «чи це
  українська» описувала стан на момент написання, а не правило; правило —
  «англійська без параметра, решта з `?lang=`», і тест
  `copy-corrections.test.ts` тепер вимагає його для всіх пʼяти мов.
- **`Emulation.setPageScaleFactor(2)` — це щипок, а не Ctrl+Plus.** Page
  scale масштабує візуальне вікно (`visualViewport.scale = 2`), а
  layout-вікно й компонування не змінюються. Ctrl+Plus у десктопному
  Chrome робить інше: CSS-вікно стає вдвічі вужчим, DPR подвоюється,
  сторінка перекомпоновується. Справжнього браузерного зуму в headless
  Chromium через Playwright немає, тож доказ несе два окремо названі
  сценарії — page-scale і reflow (720 CSS px при DPR 2) — і жоден не
  зветься Ctrl+Plus. `visualViewport.scale = 2` сам по собі доводить лише
  page-scale.
- **Довільний варіант Tailwind із двокрапкою всередині дужок не потрапляє у
  збірку.** `[&_th:not(:first-child)]:ps-6` виглядає як звичайний клас, тест
  типів на нього не скаржиться, у розмітці він присутній — і не робить нічого:
  сканер класів обриває розбір на двокрапці в `:not(:first-child)`. Помітно це
  лише вимірюванням: правка «зроблена», а зазор лишається нульовим. Складне
  правило пишеться звичайним CSS зі своїм класом, і поруч має стояти причина —
  інакше наступний розробник поверне «коротший» варіант.
- **Відступ живе ВСЕРЕДІНІ клітинки, тож зазор між клітинками завжди нуль.**
  Перевіряючи, чи розійшлися колонки таблиці, я міряв різницю меж сусідніх
  прямокутників і двічі отримав 0px — спершу на зламаному CSS, потім на
  робочому. Прямокутники клітинок торкаються за побудовою; читач бачить
  відстань між ТЕКСТОМ, і міряти треба саме її (`Range.getBoundingClientRect`
  на вмісті клітинки). Вимірювання не тієї величини гірше за його відсутність:
  воно каже «не працює» про робочу правку.
- **`overflow-x: auto` вмикає прокрутку і по вертикалі.** За специфікацією,
  щойно одна вісь перестає бути `visible`, друга обчислюється в `auto`. Кнопка
  активної вкладки зсунута на піксель униз (`-mb-px`), щоб підкреслення накрило
  лінію контейнера, — і цей один піксель ставав вертикальною смугою прокрутки,
  а саме підкреслення зникало під краєм. Будь-який негативний відступ усередині
  прокрутного контейнера потребує місця: тут вистачило `pb-px`.
- **Ціна живе в одному місці, а прайс провайдера — її наслідок.** Дві правди
  про одну суму розійшлися рівно так, як мали: закладка «Ціни» показувала
  9.99, єдиний прайс у Paddle був 10.00, і клієнт платив 10.00 — у касу йде
  лише `price_id`, а суму рахує провайдер, тож наше число було підписом до
  чужої дії. Тепер збереження ціни ПУБЛІКУЄ її: створює або оновлює прайс і
  запамʼятовує `pri_…` поруч із записом. Окремого налаштування «прайс
  разової покупки» немає — гість купує ту саму «разову перевірку» каталогу,
  що стоїть на сторінці цін.
- **Публікація йде ДО запису в базу.** Відмова провайдера — 502, і ціна
  лишається старою: сайт не сміє показувати суму, за якою каса не візьме
  гроші. Виняток один — зміна провайдера, оточення чи ключа: там
  налаштування зберігаються ПОПРИ збій публікації, інакше неправильний ключ
  неможливо виправити. Записи, що не опублікувались, лишаються з попереднім
  провайдером, і кабінет називає кожен.
- **Провайдер — властивість ціни, а не частина її ідентичності.** Ціна
  тарифу впізнається за (валюта, період). Поки в ключі стояв ще й
  провайдер, зміна каси створювала другий рядок, і повернення до
  попереднього провайдера відкривало б касу старою сумою.
- **Прайс іншого оточення — не «його немає» і не «він наш».** `pri_…`
  пісочниці в бойовому оточенні дає 404, і тоді створюється новий прайс, а
  не оновлюється чужий. Тому GET перед PATCH — крок правила, а не
  оптимізація. Так само з періодом: `billing_cycle` у Paddle не редагується,
  місячний → річний вимагає нового прайса на тому самому продукті.
- **Мова сайту губиться на ВХОДІ в кабінет, а не на виході.** У кабінету
  немає мовного префікса в адресі, а профіль знає лише дві мови, якими
  кабінет існує. Тож /de → кабінет → «на сайт» вело на англійську головну, і
  виглядало це як втрата при виході. Остання публічна сторінка тепер
  памʼятається в браузері (`crawldy_site_locale`), і всі дороги назад
  будуються з неї, а не з профілю.
- **Сторож кабінету перекриває редирект виходу.** Вихід ставив
  `/login?lang=uk`, але одразу після `clear()` спрацьовував сторож «немає
  сесії» і ставив `/login` — мова зникала при повністю правильному коді
  виходу. Мову мусять нести обидва переходи; перевірено прогоном сайт →
  вхід → кабінет → вихід → сайт для шести мов і двох ролей.
- **Порт, що відповідає, не доводить, що відповідає ТВІЙ процес.** Новий
  uvicorn не забіндився («only one usage of each socket address») і тихо
  вимкнувся, старий від учора далі слухав :8000, `/docs` віддавав 200 — а
  сторінка кабінету падала на полі, якого стара версія не знала. Дивись на
  PID і час старту процесу, що слухає порт (`Get-NetTCPConnection`), а не на
  код відповіді. Розширення пастки «сервер може бути старою збіркою».
- **Ключ, що читає, не обовʼязково пише, і перевірка зʼєднання цього не
  бачить.** Ключ Paddle власника віддавав `GET /event-types` з кодом 200 —
  тобто «Ключ прийнято провайдером», — і той самий ключ відповідав 403 на
  `POST /products`: `not authorized to create|read product`. Права ключа
  Paddle не показує жодним запитом, тож єдиний спосіб дізнатися — спробувати
  записати. Звідси три речі: 403 — окремий стан (`forbidden`), а не «невірний
  ключ»; його текст називає саме ті права, які треба увімкнути; а підпис
  перевірки зʼєднання каже «перевірено читання», щоб зелений значок не
  обіцяв більшого, ніж перевірив.
- **Загальне «Server error (5xx)» ковтало авторський текст.** Клієнт API
  свідомо ховає тіло серверних помилок, і це правильно для необробленої
  помилки. Але наш 502 несе рівно те речення, заради якого існує: чому
  провайдер відмовив і що ввімкнути. Ознака, за якою їх видно розрізнити, —
  наявність поля `detail`: у необробленої помилки FastAPI його немає взагалі.
- **Дорога до каси не має проходити через кабінет.** Кнопки сторінки цін
  вели на `/app/plan?buy=`, тобто той, хто вже увійшов, бачив «Тариф і
  використання» замість оплати, а той, хто ні, — ще й спалах форми входу
  посеред дороги. Тепер обидві ведуть на `/checkout?offer=` / `?plan=`, і
  вхід, якщо він потрібен, влаштовує сама сторінка оплати: 401 від каси —
  це `/login?next=` назад у ту саму касу. Кабінет лишився рівно на одному
  шляху: коли підписка вже є (409), тобто ЗАМІСТЬ оплати, а не перед нею.
- **Стан, що приходить після першого рендеру, подвоює ефект.** Мова
  сторінки оплати читається з адреси в ефекті (`en` → `uk`), і поки вона
  стояла в залежностях ефекту, каса відкривалася ДВІЧІ: дві транзакції у
  провайдера й дві незавершені покупки на одну людину. Видно лише в
  журналі запитів — на екрані все виглядало правильно. Дія, що створює
  щось у зовнішньому сервісі, потребує сторожа (`ref`), а не лише
  правильного списку залежностей.
- **Намір `?next=` переживає зміну людини.** Вихід із адмінки лишає в
  адресі `next=/admin`; хто створив на тій самій формі НОВИЙ акаунт,
  потрапляв на службову сторінку й бачив «доступно лише команді
  Crawldy» замість кабінету. `landingFor` тепер відкидає ціль, якої ця
  роль виконати не може. Правило ширше за цей випадок: збережений намір
  належить адресі, а не людині, і після автентифікації його треба
  перевіряти проти того, хто саме увійшов.
- **Мова профілю головніша за памʼять браузера.** Перша версія памʼяті
  мови сайту робила навпаки, і власник з українським кабінетом
  потрапляв на англійську головну — просто тому, що колись у цьому
  браузері відкривав англійську сторінку. Профіль — свідомий вибір,
  памʼять — слід випадкового візиту. Памʼять лишається для мов, яких у
  профілі бути не може: кабінет говорить двома мовами, сайт шістьма.
- **Мова інтерфейсу вже підставлена, і по ній не видно порожнього
  профілю.** `useLocale()` віддає `en` і тому, хто обрав англійську, і
  тому, у кого мови немає взагалі. Дорога назад на сайт питає саме
  профіль, тож їй потрібне СИРЕ значення: `AppShell` бере його окремим
  входом, а не з контексту. Інакше німець із порожнім профілем
  виглядав би англійцем, і памʼять браузера не спрацьовувала б ніколи.
- **Кабінет клієнта заявлений шістьма мовами, а каталог має дві.**
  Виміряно на 2026-09-06: 344 ключі в англійському словнику, 372 в
  українському, 103 у німецькому, іспанському й французькому, 113 у
  російському — тобто 241 рядок кожній із чотирьох мов бракує.
  `COMPLETE_LOCALES` тому й називається так: він перелічує мови, якими
  кабінет справді написаний, а меню мов показує саме його. Розширення
  до шести — це переклад 241 рядка, а не зміна константи.
- **Адреса каси від Paddle веде на НАШУ сторінку оплати, а не на його.**
  Він будує її з «default payment link» акаунта, тож локально це
  `https://localhost:3000/checkout?_ptxn=…`, чого не існує. Кнопка
  «Купити» в кабінеті йшла туди першим ходом і вмирала на
  `ERR_SSL_PROTOCOL_ERROR`, тоді як сусідня «Підписатися» працювала —
  бо та відкривала накладну касу через Paddle.js. Правило: усі три шляхи
  покупки (гість, кабінет, сторінка оплати) починають з
  `openPaddleOverlay`, а перехід за адресою лишається запасним. Тест
  вимагає, щоб кожен перехід стояв під умовою «накладку не відкрито».
  Заразом: у проді default payment link мусить вказувати на справжній
  домен, інакше запасний шлях приведе в нікуди.
- **Оплата пройшла, а кабінет мовчав.** Права видає лише перевірена подія
  провайдера — і це правильно. Але коли подія не приходить (локальний
  стенд, куди Paddle не достукається; збій доставки в проді), людина
  бачить порожній кабінет одразу після списання, і мовчання читається як
  «гроші зникли». Тепер кабінет питає провайдера про кілька останніх
  незавершених покупок і каже: оплату отримано, доступ буде після
  підтвердження. Прав це не видає й видати не може — функція нічого не
  змінює. Питати саме кілька, а не одну: у реальному випадку оплаченою
  була передостання каса, бо після оплати людина відкрила ще одну й
  покинула. І не всі: покинута каса лишає рядок назавжди.
- **Кнопка, що мовчить на помилку, читається як зламана.** «Платежі й
  квитанції» ковтала будь-який збій (`.catch(() => undefined)`), а 404
  там означає буденне «платіжного профілю ще немає». Власник вирішив, що
  кнопка зламана. Мовчазний `catch` у обробнику кнопки — завжди дефект:
  або показуй причину, або не лови.
- **Прайси памʼятаються по провайдерах, а не в одному слоті.** Чинну
  привʼязку тримають `provider` і `provider_price_ref`; мапа
  `provider_refs` памʼятає, що запис мав у КОЖНОГО провайдера. Без неї
  перемикання каси (наприклад, на фейкову для перевірки й назад)
  створювало б у провайдера нові продукти щоразу — і акаунт заростав би
  дублікатами від самої лише діагностики.
- **Права ключа провайдера відкриваються по одному, і кожне мовчить
  окремо.** Ключ Paddle читав перелік типів подій (перевірка зʼєднання
  зелена), не міг створити продукт (`product.write`), а потім не міг
  відкрити портал квитанцій (`customer-portal-session`). Кожна відмова —
  окремий 403 в окремому місці продукту, і жодна не видна, поки туди не
  дійдеш. Тому всі службові шляхи до провайдера мусять називати його ж
  `code` і `detail`, а не «forbidden»: без цього кожне право шукається
  наосліп.
- **Разова покупка не запамʼятовувала покупця провайдера.** Організація
  для неї береться з НАШОГО запису, тож `_organization_for` на цьому
  шляху не викликається — а відображення покупця створювалось саме там.
  Наслідок бачив клієнт: пакет оплачено, а «Платежі й квитанції» не
  відкриваються, бо портал провайдера адресується покупцем. Тепер
  відображення пишеться при підтвердженні оплати; прав це не додає.
- **Ручне зарахування не має власних повноважень.** Сторінка «Зарахування
  оплат» не відкриває доступ — вона питає провайдера і зараховує лише те,
  що він САМ називає оплаченим. Тому кнопок дві й вони різні: «Звірити»
  читає, «Зарахувати» читає ще раз і видає. Питати вдруге обовʼязково:
  між натисканнями могло минути скільки завгодно, а гроші могли
  повернути.
- **Провайдер відповідає про транзакцію, а не про наш рядок.** На одну
  оплату буває два наші рядки (дві вкладки, дві каси), і на питання про
  кожен провайдер скаже «оплачено». Зарахувати обидва означало б видати
  вдвічі більше, ніж куплено, тож перед видачею перевіряється, чи не
  оплачувала ця транзакція вже іншу покупку.
- **Сума покупки до оплати нульова.** `amount_minor` заповнює подія
  оплати, тож у переліку незарахованих він завжди 0, а `currency`
  порожня. Ціна замовленого береться зі зліпка умов, знятого при
  відкритті каси; скільки провайдер узяв насправді, каже звірка — і ці
  числа різні (49.99 у нас проти 53.29 у Paddle: податок).
- **Перелік незарахованих оплат — це переважно покинуті каси.** Кожне
  натискання «Купити» відкриває касу й лишає рядок назавжди, заплатила
  людина чи ні. На живих даних власника таких 32, а справді оплачена й
  незарахована — одна. Тому сторінка має «Звірити всі» однією дією
  (паралельно, по пʼять запитів) — шукати голку тридцятьма натисканнями
  ніхто не буде.
- **Паралельні запити не діляться сесією SQLAlchemy.** Перша версія
  масової звірки викликала `verify(db, …)` під `asyncio.gather`, тобто
  тридцять корутин на одну сесію. Тепер база читається ЦІЛКОМ до
  паралельної частини, а запити до провайдера сесії не торкаються
  взагалі.
- **Покинуту касу гасять СТАНОМ, а не видаленням рядка.** Перша версія
  прибирала рядки `DELETE`, і це було двічі неправильно: `audit_unlocks`
  посилається на покупку з `ON DELETE RESTRICT` (рядок із відкритим
  доступом не видалився б узагалі), а головне — оплата, що прийде
  пізніше, не знайшла б свого запису, і подія лягла б у журнал збоєм.
  `PurchaseStatus.ABANDONED` вирішує обидва: перелік незарахованих
  чиститься (у ньому лише PENDING), рядок лишається, а `mark_paid`
  оживляє покупку. Це зробило непотрібним вікно «зачекати тиждень»:
  помилка гасіння коштує рядок у списку, а не гроші клієнта.
- **Гасити можна те, про що провайдер сказав «не оплачено», і те, чий
  провайдер більше не обслуговує касу.** «Не знаємо» не гаситься ніколи:
  мовчання провайдера — не відповідь. Друга категорія потрібна для
  записів, що лишились від попереднього провайдера: нову оплату через
  нього ми не приймаємо, а стара, якщо прийде, оживить запис.
- **Число на кнопці мусить бути зобовʼязанням, а не збігом.** Поки
  підрахунок і застосування були двома незалежними опитуваннями
  провайдера, «Погасити 2» могло погасити нуль або сім. Тепер підрахунок
  повертає ІДЕНТИФІКАТОРИ, згода надсилає їх назад, і гасяться лише ті з
  них, що й далі підпадають під правило: набір звужується, ніколи не
  росте.
- **Нуль без знаменника читається як поломка.** «Прибрати 0» над повним
  списком власник прочитав як зламану кнопку — хоча дія була правильна:
  єдиний придатний рядок вона прибрала попереднім натисканням. Поруч із
  числом тепер стоїть увесь розклад: скільки незарахованих усього,
  скільки звірено, скільки не оплачено, скільки чужого провайдера,
  скільки оплачено, скільки без відповіді. Той самий клас, що «+0 до
  бала».
- **Ширина колонки статусу мовчки обмежує перелік станів.** `status` був
  `varchar(8)` — рівно під найдовше з наявних значень (`REFUNDED`), і
  новий `ABANDONED` не влазив на рівні бази. Помилка вилазить лише під
  час запису, у тесті, а не на імпорті: додаючи значення в `StrEnum`, що
  зберігається як рядок, дивись ширину колонки.
- **Стан, що ховає рядки з переліку, потребує способу їх побачити.**
  Гасіння прибрало 31 касу з екрана, і власник запитав «куди все
  щезло»: рядки були цілі, але подивитися на них не було де. Перемикач
  «показати погашені» — не зручність, а умова того, щоб дія лишалась
  зрозумілою. Заразом погашену касу МОЖНА зарахувати: якщо провайдер
  каже, що заплатили, оператор не має шукати обхідних шляхів.
- **Порожня таблиця — стан, а не привід ховати функціонал.** Кнопки
  дій були під `rows.length > 0`, і разом із рядками зникли самі дії:
  екран виглядав так, ніби сторінку зламано. Дії лишаються на місці
  завжди, вимкненими, коли діяти нема на чому.

## Що робити далі

Стан і пріоритети — в `ROADMAP.md`. Найближче:

**Фаза 1 закрита.** `GET /v1/audits/{id}/report?format=json|docx&lang=uk|en&target=<id>`, кілька URL через `audit_targets`, публічні посилання `/r/{token}`.

Наступне — **фаза 4, SaaS-обвʼязка**: auth, білінг, заплановані аудити, історія скорів. PDF свідомо відкладений.

Історія скорів зіткнеться з тим, що друга стеля змінила бали: аудити до
неї й після неї порівнювати не можна. Або перерахувати збережені, або
позначити версію скорингу в записі.

**Фаза 2 — Playwright.** JS-рендеринг, waterfall, вплив third-party скриптів, SSR-дельта (текст без JS проти тексту після рендеру), mobile vs desktop в одному звіті, Lighthouse-сайдкар.

**Фаза 3 — LLM-шар.** Опційний семантичний аналіз, генерація llms.txt за структурою сайту, пріоритезований план дій.

**Фаза 4 — SaaS-обв'язка.** Auth, білінг, заплановані аудити, історія скорів.

## Самостійне мислення

Не будь пасивним виконавцем. Оцінюй запропоновані зміни самостійно — проти
доказів Crawldy, його архітектури, обсягу продукту й ухвалених раніше рішень.

Незгода очікується там, де видно ризик коректності, сильнішу альтернативу,
приховану ціну, конфлікт з архітектурою або недостатній доказ. Кажи про неї
**до** реалізації й одразу називай, що пропонуєш натомість.

Явне продуктове рішення мовчки не перекривай. Незгоду, що зачіпає напрям
продукту, архітектуру, скоринг, обсяг або методологію, виноси на розмову
перш ніж міняти код.

Обмеження на самостійні зміни не обмежують аналіз, критику й пропозиції.

## Конвенції

- Типізація скрізь; `mypy --strict` має проходити на `app/audit/`.
- Функції маленькі й тестовані; парсинг окремо від оркестрації.
- Pydantic для схем API, SQLAlchemy для персистентності, async там, де є I/O.
- Таймаути й фолбеки на кожному зовнішньому виклику. Мережа падає — це нормальний сценарій, а не виняткова ситуація.
- Мова коду й коментарів — українська для доменних пояснень, англійська для ідентифікаторів.
- Рядки issue (`title`, `description`, `recommendation`) пише людина для клієнта: конкретно, без загальних фраз на кшталт «оптимізуйте сайт». Обидві мови рівноправні — англійська не підрядковий переклад української.
- Якщо щось неясно — сформулюй припущення, задокументуй його в `ARCHITECTURE.md` і рухайся далі. Не блокуйся на уточненнях.
