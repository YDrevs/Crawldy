# Архітектура — AI Site Audit Agent (MVP)

## 1. Продукт у двох реченнях

SaaS, який за URL робить аудит сайту в шести вимірах: **швидкість/UX**, **базове SEO**, **AI-ready/LLMO**, **придатність до цитування**, **захист і аналітика**, **доступність** — і повертає скор 0..100 з переліком проблем, доказів та рекомендацій.

Ключова відмінність від Ahrefs/Screaming Frog: блок LLMO (llms.txt, entity signals, семантична ясність, придатність контенту до цитування моделями).

Четвертий вимір називається саме придатністю, а не видимістю: зовнішнього тестування промптами ми не робимо, і назва не має обіцяти того, чого ми не міряємо. Внутрішній ключ модуля лишається `llm_visibility` — його бачить лише база, і міграція заради косметики зробила б непорівнянними всі збережені аудити.

## 2. Стек

| Шар | Технологія | Обґрунтування |
|---|---|---|
| API | Python 3.12 + FastAPI + Pydantic v2 | async I/O, OpenAPI з коробки |
| Черга задач | ARQ (Redis) | asyncio-native, простіше за Celery для async-краулера |
| БД | PostgreSQL 16 + SQLAlchemy 2.0 (async) + Alembic | JSONB для сирих результатів чеків |
| HTTP-клієнт | httpx (AsyncClient, HTTP/2) | таймаути, редіректи, пул з'єднань |
| Парсинг | selectolax (HTML) + extruct/json | selectolax у ~5-10× швидший за BeautifulSoup |
| Performance | `PerformanceProvider` → PSI API \| self-hosted Lighthouse | див. §6 |
| Кеш/локи | Redis | дедуплікація аудитів, rate-limit |
| Фронт | Next.js 15 (App Router) + Tailwind | мінімальний dashboard |
| Обсервабіліті | structlog + OpenTelemetry (опц.) | структурні логи з `audit_id` |

**Припущення (задокументовані):**
- A1. MVP аудитує **до 50 сторінок** на сайт (ліміт краулера), глибина 2. Enterprise-краул — поза скоупом.
- A2. Один аудит = один домен + одна точка входу. Мультирегіональність/hreflang — фаза 3.
- A3. LLM-виклики (для семантичного аналізу) — опційні; без API-ключа модуль повертає лише детерміністичні евристики.
- A4. Аутентифікація в MVP — API-ключ у заголовку. Повний auth/billing — фаза 4.

## 3. Топологія

```
                    ┌──────────────┐
   Next.js  ───────▶│  FastAPI     │  POST /v1/audits  → 202 + audit_id
   dashboard        │  (api)       │  GET  /v1/audits/{id}
                    └──────┬───────┘
                           │ enqueue (ARQ)
                           ▼
                    ┌──────────────┐        ┌────────────────────┐
                    │  Redis       │◀──────▶│  worker (ARQ)      │
                    └──────────────┘        │  run_audit()       │
                           ▲                └─────────┬──────────┘
                           │ cache                    │
                    ┌──────┴───────┐                  ▼
                    │  Postgres    │◀────── orchestrator: crawl → checks → score
                    └──────────────┘                  │
                                          ┌───────────┴────────────┐
                                          ▼                        ▼
                                   PSI API / Lighthouse      HTTP fetcher
```

API-процес **ніколи** не робить зовнішніх мережевих викликів для аудиту — тільки постановка задачі й читання результатів. Це тримає p99 API < 100 мс.

## 4. Модель даних

```
audits
  id            uuid  pk
  url           text            -- нормалізований вхідний URL
  origin        text            -- scheme://host
  status        enum(queued, running, completed, failed, partial)
  options       jsonb           -- {max_pages, strategy, modules[]}
  score_overall smallint null
  scores        jsonb null      -- {performance, seo, ai_ready, llm_visibility}
  error         text null
  created_at / started_at / finished_at  timestamptz

audit_pages
  id         uuid pk
  audit_id   uuid fk → audits (cascade)
  url        text
  status_code / content_type / html_bytes / response_ms
  depth      smallint
  raw        jsonb           -- витягнуті сигнали сторінки (title, meta, headings, jsonld…)

audit_targets                -- одна ціль аудиту: свій краул, свій скор
  versions   jsonb             -- чим саме порахований аудит (0005)
  snapshot   jsonb             -- зібране без втрат для перерахунку (0006)

issue_verdicts               -- що сказала людина про знахідку (0007)
  issue_id   uuid fk unique    -- один вердикт на знахідку, оновлюється
  code / msg text              -- дублюються навмисно: переживають видалення аудиту
  verdict    enum(agreed, fixed, wont_fix, wrong, unclear)
  note / author text

audit_issues
  id         uuid pk
  audit_id   uuid fk
  page_id    uuid fk null      -- null = проблема рівня сайту
  module     enum(performance, seo, ai_ready, llm_visibility, tech, accessibility)
  code       text              -- 'seo.title.missing'
  severity   enum(critical, high, medium, low, info)
  title / description / recommendation  text
  evidence   jsonb             -- {found: "...", expected: "..."}
  weight     smallint          -- внесок у штраф скора
  issue_variant text           -- варіант проблеми; code + variant = issue_key
  msg_key    text              -- ключ каталогу i18n
  msg_params jsonb             -- параметри шаблону
```

Міграція 0002 додала до `audits` ще `degraded`, `skipped_modules`, `evidence` (jsonb): без них звіт не зібрати з БД. Деградації раніше жили склеєним рядком в `error`, а site-level докази — лише в `SiteContext` і після аудиту зникали.

Індекси: `audit_issues(audit_id, module, severity)`, `audit_pages(audit_id, url)`, `audits(created_at desc)`.

**Чому issues окремою таблицею, а не одним JSONB:** потрібні агрегації («топ-10 проблем по всіх аудитах клієнта») і фільтри у звіті без парсингу JSON.

## 5. Пайплайн аудиту

```
run_audit(audit_id)
 ├─ 1. resolve()      нормалізація URL, DNS, редіректи, вибір канонічного origin
 ├─ 2. site_context() robots.txt, sitemap.xml, llms.txt, favicon, HTTPS/HSTS
 ├─ 3. crawl()        BFS від точки входу, ліміт max_pages/depth, повага до robots
 ├─ 4. extract()      на кожну сторінку → PageSignals (детерміністичний парсинг)
 ├─ 4б. site_facts()  зведення фактів сайту + граф посилань (link_graph)
 ├─ 5. checks()       паралельно: SEO, AI-ready, LLM-visibility (на PageSignals)
 │                    + performance (PSI/Lighthouse на 1-3 ключових URL)
 ├─ 6. score()        зважений скор по модулях
 └─ 7. persist()      issues + scores → Postgres, status=completed
```

Кожен крок — окрема функція з таймаутом. Падіння одного модуля → `status=partial`, а не `failed`: користувач отримує часткові дані.

## 6. Абстракція performance-провайдера

```python
class PerformanceProvider(Protocol):
    name: str
    async def measure(self, url: str, strategy: Strategy) -> PerformanceResult: ...
```

- `PsiProvider` — Google PageSpeed Insights API. Дає lab (Lighthouse) + field (CrUX). Ліміт 25 000 запитів/добу з ключем, ~400 запитів/100 сек. Нуль інфраструктури.
- `LighthouseProvider` — власний Node-воркер (`lighthouse` + `puppeteer` у контейнері з headless Chrome), викликається через HTTP-сайдкар. Дає повний trace/waterfall і працює на staging-доменах, недоступних Google.

Вибір через `PERF_PROVIDER=psi|lighthouse|auto`. У режимі `auto`: PSI, а на 4xx/5xx або приватний хост — фолбек на Lighthouse. Нормалізований `PerformanceResult` однаковий для обох, тому чеки й скоринг про провайдера не знають.

## 7. Модулі чеків

Кожен чек — клас із `code`, `module`, `severity`, `weight` і методом `run(ctx) -> list[Issue]`. Реєстр чеків — це список, тож додати новий чек = один файл + один рядок реєстрації.

**SEO (базове):** title (наявність, довжина 30–60, дублі по сайту), meta description (50–160, дублі), H1 (рівно один), ієрархія заголовків, canonical (наявність, self-referencing, конфлікт з redirect), robots.txt (доступність, `Disallow: /`), sitemap.xml (наявність, валідність, покриття), `noindex`/`nofollow`, HTTPS, 4xx/5xx у внутрішніх лінках, глибина кліків, orphan-сторінки, alt у зображень, дублі контенту (simhash).

**Performance:** LCP, INP, CLS — справжні Core Web Vitals, лише вони можуть бути критичними; TTFB і TBT діагностичні й максимум HIGH, бо їх не переживає користувач безпосередньо. Лабораторне джерело знижує впевненість, а за наявності польового INP лабораторний TBT не повідомляється взагалі. Далі: render-blocking ресурси, невідкладені зображення, відсутність `width/height` (→ CLS), неоптимізовані формати (не WebP/AVIF), відсутність `loading=lazy` нижче фолду.

**AI-ready / LLMO:** `llms.txt` (наявність, структура, покриття ключових розділів), JSON-LD — валідність і наявність `Organization`, `WebSite`, `BreadcrumbList`, `Article`/`Product`, `FAQPage`, `HowTo`; `@id`-зв'язність сутностей; `sameAs` (Wikidata/LinkedIn/GitHub) як entity signal; OpenGraph; мова й `lang`; доступність контенту без JS (SSR-перевірка: порівняння HTML-only тексту з очікуваним обсягом).

**LLM-visibility:** чи є на сторінці пряма відповідь у перших 200 словах; співвідношення текст/розмітка; наявність структурованих блоків (списки, таблиці, FAQ); наявність About / Contact / Author-сторінок; авторство і дати; ясність бренду (назва в title/H1/schema узгоджена); читабельність; чи не заблоковані GPTBot/ClaudeBot/PerplexityBot у robots.txt (окремий сигнал — не завжди проблема, іноді свідомий вибір).

## 8. Скоринг

```
penalty      = Σ(weight_i × severity_multiplier_i)      , дві стелі на один code
module_score = 100 × half_scale / (half_scale + penalty)
overall      = 0.25·perf + 0.25·seo + 0.20·ai_ready + 0.20·llm_visibility + 0.10·tech
```

Шкала гіперболічна: монотонна, завжди в (0, 100], clamp не потрібен. `half_scale` — штраф, за якого модуль опускається до 50.

**Чому не лінійна.** Перший же реальний клієнтський сайт перевищив нормалізатори у 1.7–2.2 раза й отримав 0 по всіх чотирьох напрямах. Це не просто негарно: клієнт, що виправив половину проблем, побачив би той самий нуль. Гіпербола зберігає різницю на будь-якому рівні занедбаності, а `half_scale` удвічі менший за старий нормалізатор тримає калібрування типового сайту незмінним.

severity multipliers: critical 5, high 3, medium 2, low 1, info 0. Ваги зберігаються в конфізі (`scoring.py`), не хардкодяться в чеках — щоб калібрувати без правок логіки.

**Дві стелі на один code, а не одна.** Перша відносна — 4× від самої знахідки: одна проблема на 20 сторінках не має обнуляти модуль. Друга — частка від `half_scale` модуля, і без неї перша не працює на важких чеках. `ai.jsonld.missing` (вага 4, high) дає 12 за штуку, тобто 48 у першій стелі, при `half_scale` 30: один код опускав `ai_ready` зі 100 до 38 і фактично вирішував пʼяту частину підсумку. Наслідок був не теоретичний — занедбаний сайт на WordPress обганяв stripe.com, бо CMS роздає розмітку з коробки. Друга стеля прибрала всі інверсії рівнів на вибірці, звузивши діапазон балів лише з 45 до 38.

Одиночна знахідка рахується завжди повністю: стеля приборкує повторення, а не силу проблеми. Інакше одна критична в `tech` (5×5=25 при `half_scale` 20) обрізалась би до 10, і чек, який ловить найгірше, важив би менше за пару дрібних.

**Параметр підібрано перебором на зібраних даних.** Знахідки в `calibration.json` містять code, severity й модуль, тож бал перераховується під будь-які параметри без нового краулу: прогін вибірки коштує годину й гроші, перебір — секунду. Це єдиний спосіб не підганяти шкалу під один сайт.

## 8б. Калібрування на реальних сайтах

Юніт-тести перевіряють, що чек спрацьовує там, де його про це попросили. Вони не можуть сказати, чи він спрацьовує **не там**. Це показує лише прогін по вибірці сайтів різної якості — `scripts/calibrate.py`.

**Головна метрика — не оцінка, а частота.** Чек, що спрацьовує на 70–90% вибірки, не несе інформації: він або тривіальна істина, або наше хибне спрацювання. У першому калібруванні таких було сім із 55.

Три правила, вироблені на цій вибірці й порушення яких є багом:

**1. Кожне виправлення потребує контрприкладу з вибірки, а не міркування.** Шість виправлень, виведених з одного сайту (dronehub.ai), разом вирізали рівно його профіль: він отримав 92 при 2 знахідках, тоді як gov.uk — 47 при 69. Це не калібрування, а підгонка. Правильна форма: «чек вимагав LocalBusiness від Stripe, MDN і gov.uk, у яких його не має бути».

**2. Мовчання не винагороджується балами.** Найсерйозніша знайдена вада: сайти, що віддають агенту 403, не давали жодної знахідки й виходили на перше місце у своїй групі. Медіана односторінкових обходів — 62 бали при 17 знахідках проти 58 при 51 у повних. Порожній `ctx.ok_pages` виключає контентні модулі зі скора; `tech.crawler_blocked` читає `ctx.pages`, а не `ok_pages`, і лишається єдиним працездатним чеком, коли не працює жоден інший.

**3. Вибірка має покривати клас клієнта, а не лише зручні сайти.** Поки у вибірці були самі docs-сайти рівня Stripe і Vercel, пʼять чеків (`ai.schema.contact` і вся NAP-консистентність) не мали жодного прикладу й були фактично мертві — жоден прогін не доводив, що вони працюють. Локальний бізнес із адресою й телефоном оживив їх одразу: 12 спрацювань із 18.

**Мала вибірка бреше в потрібний бік.** Друга стеля на код прибрала всі інверсії рівнів на 13 сайтах — і це виглядало як доведений результат. На 30 сайтах вона їх лише зменшила з 14 до 6, а нуля дійшла тільки після того, як знайшлась справжня причина решти: ka-dent.com.ua був позначений «низьким» помилково. Він має розділ послуг із семи сторінок, адресу, телефон, імена лікарів і JSON-LD — тобто рівно те, що аудит міряє. Розбіжність між гіпотезою й оцінкою вказала не на дефект шкали, а на дефект гіпотези, і це нормальний результат калібрування, а не виняток. Вибірка лежить у `scripts/samples/calibration.txt`.

**Рівень шкали й порядок — різні речі.** Множник до всіх `half_scale` не міняє порядок узагалі: на 30 сайтах будь-яке значення від 0.5 до 1.2 дає нуль інверсій, зсуваючи лише самі числа (занедбаний сайт від 37 до 55). Тобто це вибір, де проходять межі смуг, а не калібрування. Зовнішніх даних, якими його можна обґрунтувати — наприклад, зв'язку балу з реальними зверненнями клієнтів, — у нас немає, тож множник лишається як є. Крутити його «на око» означало б додати рівно той борг, який уже записаний нижче.

**Калібрування не платить за семантику.** `calibrate.py` вимикає LLM-шар за замовчуванням (`--llm` вмикає). Від нього залежить один чек із 58, а прогін на 30 сайтів коштує 60 викликів моделі й нічого не додає до відповіді на питання «чи розводить шкала».

**Перша зовнішня перевірка знайшла те, чого не знайшла жодна внутрішня.** Користувач зробив аудит furniturerow.com і поруч спитав чотири асистенти «best furniture stores in Tyler»: Perplexity і Copilot назвали компанію першою, Gemini у середині, ChatGPT не згадав, а Google показав її в локальному блоці, але не в органіці. Розбір цієї розбіжності виявив три дефекти, з яких жоден не був видимий ні тестам, ні калібруванню:

1. У контейнері не було браузера — уся фаза 2 не працювала жодного разу через докер, і кожен аудит через UI був `partial`.
2. Карта сайту бралася початком, тож сторінки магазинів не потрапляли ні в засів, ні в краул — і звіт радив клієнту додати розмітку, яка в нього була.
3. У каталозі порад стояв український номер прикладом, який читав американський клієнт.

Спільне в усіх трьох: система поводилась чесно — писала `partial`, називала причину, показувала докази. Не спрацювало те, що ці слова треба було прочитати. Внутрішня перевірка дивиться, чи код робить, що написано; зовнішня — чи написане має сенс.

**Відтворюваність обмежена ззовні.** Захист від ботів реагує на повторні візити: openai.com в одному прогоні віддав 8 сторінок і 75 балів, у наступному — 403 і 36. Обходити захист не можна; правильна поведінка — чесно показати блокування у звіті, що аудит і робить.

## 8а. Шар звітів (фаза 1)

```
AuditOutcome  ─┐
               ├─→ ReportSource ─→ ReportDocument ─→ JSON | docx
рядки БД      ─┘
```

`app/report/` тримає той самий інваріант чистоти, що й `app/audit/`: ні FastAPI, ні SQLAlchemy. Адаптер із ORM живе в `services/report_service.py`, тож білдер один на обидва шляхи — свіжий аудит і давно збережений.

**Ідентифікатор проблеми окремо від її тексту.** `code` — категорія детектора, `issue_key` (`code:variant`) — конкретна проблема, `msg` — рядок каталогу. Стеля штрафу й групування рекомендацій тримаються на `issue_key`; `msg` лишається presentation layer і ідентифікатором бути не може, бо міняється разом із формулюванням. Варіанти оголошуються на чеку (`Check.variants`), а не виводяться з повідомлень: інакше редагування тексту мовчки зсувало б бали.

**Локалізація.** Чек не пише текст, а віддає ключ каталогу і параметри (`Issue.msg`, `Issue.params`). `Check.issue()` одразу рендерить у дефолтну локаль, тому `Issue.title` заповнений як і до i18n, а шар звіту перерендерює те саме іншою мовою. `msg_key`/`msg_params` персистяться — без них збережений аудит не перекласти.

Мова обирається на рівні артефакту (`?lang=uk|en`), а не всередині файлу: один запит → один документ → одна мова.

**Три рівні деталізації** з одних даних:

| Рівень | Гранулярність | Розмір | Для кого |
|---|---|---|---|
| `issues` | одне входження | 30–500 | машина, дебаг |
| `recommendations` | згруповано по `issue_key` | 10–25 | виконавець |
| `next_actions` | топ-7 по `impact / effort` | 7 | той, хто вирішує |

**Пріоритезація.** `impact_points` рахується наявним скорером: прибрати групу з набору issues і перерахувати `compute_scores`. Другої евристики, яку довелося б окремо калібрувати, немає, і число означає рівно те, що каже.

Пастка: коли модуль уже заклампаний до 0, різниця скорів після будь-якого фікса дорівнює нулю. Тому ранжування йде по `overall_raw` (без clamp), а показується чесна заклампана дельта з прапорцем `floored`. `impact_points` різних пунктів **не адитивні** — про це каже `summary.impact_is_independent`.

`effort` — статичний атрибут класу `Check`, поруч із `weight`. Дані декларуються біля чека, а не вгадуються в шарі звіту.

**Важливість сторінки.** Вигода на вартість була єдиним, що впорядковувало пункти всередині смуги, і знахідка на головній важила стільки ж, скільки знахідка на забутій сторінці третього рівня. `app/audit/link_graph.py` будує граф із посилань прочитаних сторінок і рахує важливість кожної з двох сигналів, які подає сам сайт: скільки сторінок на неї посилаються (0.65) і на якій вона глибині (0.35). Головна — одиниця за побудовою.

Число лягає в `Issue.evidence["page_importance"]`, а не в окреме поле моделі: `evidence` уже персиститься як JSONB, тож перебудова звіту з бази дає той самий порядок без міграції. Множник у пріоритеті — `0.5 + 0.5 × importance`: забута сторінка втрачає половину ваги, але не всю, бо нуль означав би «виправляти там нічого». Знахідка про сайт загалом сторінки не має й не втрачає нічого.

Важливість групи — максимум, а не середнє: проблема, що є і на головній, і на десятку забутих сторінок, лишається проблемою головної, і середнє розмило б її саме масштабом ураження.

**Межа графа.** Він побудований з того, що ми прочитали, тому «на цю сторінку ніхто не посилається» — твердження про вибірку рівно тією мірою, якою вибірка менша за сайт. `seo.orphan_pages` тому має гейт покриття карти сайту (`SITEMAP_COVERAGE_FOR_ORPHANS`), а `seo.links_to_noindex` — ні: там обидві половини суперечності бачив сам аудит.

**Прогалини.** `Degradation` (scope / kind / reason / affected_modules) → `missing_data` у звіті. `MODULE_EXCLUDED` — свідоме вимкнення, `PARTIAL_DATA` — оцінили тим, що маємо; жодне з них не робить аудит `failed`.

**Три стани покриття модуля.** Раніше було два — «є дані» і «нема». Але без ключа PSI ми все одно міряємо час відповіді сервера самі, тож напрям не порожній. Тому: `skipped` (нема нічого або вимкнено) → `speed_score: null`; `partial` (є власні вимірювання, нема CWV) → оцінка є, `ScoreEntry.partial=true`, застереження в `missing_data`; повний → звичайна оцінка. Компроміс усвідомлений: швидкий сервер із поганим LCP отримає завищену оцінку, тому неповнота проговорена у звіті явно.

**Дві аудиторії одного документа.** Word-звіт ділиться на частину для того, хто ухвалює рішення, і частину для того, хто виправляє. Перша будується на полі `consequence` з каталогу — одне речення про наслідок для бізнесу, без жаргону, обовʼязкове для кожного ключа. Воно не зберігається в БД: береться з каталогу за `msg_key`, тож переклад і переформулювання не потребують міграції.

## 8в. Шар даних: перерахунок, історія, вердикти, конкуренти

Чотири речі, які разом відповідають на питання «а чи стало краще» так,
щоб відповіді можна було вірити.

**Знімок** (`app/audit/snapshot.py`, `audit_targets.snapshot`). До нього
в базі лежали висновки, а не сигнали: `PageSignals.to_json()` навмисно
компактний — посилання згорнуті в лічильники, розмітка в перелік типів,
тексту немає. Зібрати з нього `SiteContext` назад неможливо, тож єдиним
способом оновити бал після зміни правил був повторний краул, тобто
вимірювання вже іншого сайту.

Знімок серіалізує зібране без втрат, `orchestrator.rescore()` проганяє
по ньому чеки й скоринг без жодного мережевого виклику. Похідні дані
(`known`, `links`) рахуються заново: нова версія коду має отримати їх за
новими правилами, а не дістати законсервованими. HTML і висновки моделі
не зберігаються — перші не потрібні чекам, другі належать конкретному
прогону.

Це ж інструмент калібрування. Два прогони `calibrate.py` — це два різні
краули, і розкид між ними (медіана 2 бали, максимум 7) більший за
більшість змін, які ми оцінюємо. Зміну правил міряють `rescore_dir.py`
до і після на тих самих знімках; інакше читаєш шум і приписуєш його
своїй правці.

**Історія** (`app/report/history.py`). Дельта рахується завжди, але поруч
стоїть відповідь на питання, якого клієнт не поставить: чи змінювалися
`detector` і `scoring`. Якщо так — різниця пояснюється і сайтом, і нами,
а розділити внески неможливо. `config` і `model` на це не впливають:
вони кажуть, *що* міряли, а не *як* рахували. Там, де в старого аудиту є
знімок, порівняння лікується перерахунком.

**Вердикти** (`issue_verdicts`). Єдине джерело зовнішньої правди, яке в
проєкту може зʼявитися: калібрування досі спиралося на гіпотезу про
рівень сайту, і звіряти її не було з чим. Головне рішення тут — не
збирати вердикти, а розділити їх: `wrong` («такого немає») свідчить
проти чека, `wont_fix` — про пріоритети клієнта, `unclear` — про наше
формулювання. Одна кнопка «відхилити» зробила б усі три однаково
марними як дані.

**Конкуренти** (`app/report/benchmark.py`). Аудит на кілька URL — це вже
ви й конкуренти; бракувало прочитання. Таблиця балів найменш корисна:
значення має поділ знахідок на спільні для всіх (норма галузі), лише
ваші (те, за що платять) і лише не ваші (перевага). Порівнювати можна
тільки однаково пораховане, і сюди, на відміну від історії, входить
`config`: краул на 25 сторінок проти краулу на 5 — це порівняння
бюджетів.

## 9. Безпека й обмеження

- SSRF-захист: блокування приватних IP-діапазонів (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, ::1) після DNS-резолву, перевірка на кожному редіректі.
- Ліміти: розмір відповіді (5 МБ), таймаут запиту (15 с), таймаут аудиту (10 хв), max_pages.
- Повага до `robots.txt` і `Crawl-delay`, власний User-Agent із контактним URL.
- Rate-limit на API-ключ: N аудитів/годину (Redis token bucket).

## 10. Що свідомо НЕ входить в MVP

Бек-лінки, позиції в SERP, конкурентний аналіз, JS-рендеринг краулера (тільки статичний HTML + окремий SSR-чек), мультимовність, білінг, командні акаунти, історія/тренди по аудитах.
